## 一、规模化目标与约束

### 1.1 建议采用的容量档位（用于架构选型）

| 档位 | 学校数 | 注册学生 | 日活（DAU） | 峰值并发（同时在线） | 典型场景 |
|------|--------|----------|-------------|----------------------|----------|
| **S1 试点** | 10～50 | 1 万～5 万 | 500～2 000 | 200～500 | 单区教育局试点 |
| **S2 区域** | 100～500 | 10 万～50 万 | 2 万～10 万 | 2 000～1 万 | 省市推广、开学季高峰 |
| **S3 全国** | 2 000+ | 100 万～500 万 | 20 万～100 万 | 1 万～5 万+ | 全国联赛、多校同时开课 |

　　架构按 **S2 设计、S3 可演进**：避免过早微服务化，但在数据层预留分区、只读副本与异步分析。

### 1.2 业务与技术约束

| 约束 | 设计回应 |
|------|----------|
| 未成年人数据 | 最小必要采集、家长授权、脱敏展示、独立审计 |
| 开学季/联赛尖峰 | 无状态 API 水平扩展 + Redis + 对局 Worker 池 |
| 教师低 IT 能力 | 校级管理后台简单、支持 SSO/教育局统一身份 |
| 赛制持续增加 | CyberCore 声明式配置，见 `00-解耦声明式商业模拟框架总览.md` |
| 学校数据隔离 | 多租户 `organization_id` + 可选 Schema/库隔离 |
| 离线与弱网 | PWA + 关键接口幂等 + 对局状态服务端权威 |

## 二、总体技术栈（生产级）

### 2.1 技术栈总表（推荐「默认方案」）

| 层级 | 选型 | 说明 |
|------|------|------|
| **CDN / WAF** | 阿里云 CDN + WAF / 腾讯云等价 | 静态资源、DDoS、Bot 防护 |
| **入口** | Nginx Ingress 或云 ALB | TLS 终结、路由、限流 |
| **API 网关** | Kong / APISIX / 云 API 网关 | 鉴权、限流、灰度、审计日志 |
| **业务后端** | **Python 3.12+ FastAPI**（模块化单体） | 与现有 MVP 一致；按域分包 |
| **结算引擎** | **TypeScript `@bizsim/cybercore`** 独立包 | 纯函数、可 Worker 调用；对齐声明式框架 |
| **实时对局** | **WebSocket**（FastAPI / Socket.IO）+ **Redis Pub/Sub** | 房间状态、阶段广播 |
| **异步任务** | **Celery** + Redis 或 **RQ** | 结算、复盘、导出、榜单快照 |
| **主库 OLTP** | **PostgreSQL 16+**（RDS） | JSONB、RLS、分区、pgvector 可选 |
| **缓存** | **Redis 7**（集群） | 会话、热数据、排行榜、分布式锁 |
| **分析库** | **ClickHouse** 或 PG 分区 + 只读副本 | 决策日志、Apollo 报表 |
| **对象存储** | 阿里云 OSS / 腾讯云 COS | 课件、证书、上传作业、对局快照 |
| **向量检索** | **pgvector**（先期）→ Qdrant/Milvus（规模大时） | Athena RAG |
| **搜索（可选）** | PostgreSQL FTS / OpenSearch | 课程、Wiki、题库 |
| **前端** | React 18 + TS + Vite + TanStack Query | 学生/教师/运营多应用或路由分端 |
| **移动端** | PWA → 微信/钉钉小程序（Taro） | 家长端、通知触达 |
| **大屏** | React + ECharts / 独立 `screen-display` | 班级/联赛现场 |
| **AI** | 国内大模型 API + 自研 **ai-orchestrator** | Athena/Demia/Rival；队列削峰 |
| **容器编排** | **Kubernetes**（生产）/ Compose（开发） | HPA 按 CPU/QPS/队列深度扩缩 |
| **CI/CD** | GitHub Actions / 云效 | 镜像、迁移、金丝雀 |
| **可观测** | Prometheus + Grafana + Loki + **Sentry** | 链路追踪可选 OpenTelemetry |
| **密钥** | 云 KMS + Vault 类方案 | 数据库、API Key 轮换 |

### 2.2 为何不首选「一上来全微服务」

　　教育 SaaS 早期团队有限，**模块化单体（Modular Monolith）** 更合适：域边界清晰（identity/career/arena/ai…），单库事务简单，运维成本低。仅在以下情况拆独立服务：

- **CyberCore Worker**：结算 CPU 密集、需水平扩展  
- **ai-orchestrator**：LLM 调用慢、需独立限流与配额  
- **realtime-gateway**：WebSocket 长连接与 HTTP 分离  

### 2.3 逻辑架构图

```
                    [ CDN ] → [ WAF ] → [ Ingress / ALB ]
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   web-student          web-teacher           web-admin
         │                    │                    │
         └────────────────────┼────────────────────┘
                              ▼
                    [ API Gateway / BFF ]
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   api-service          realtime-gw         ai-orchestrator
   (FastAPI 域模块)      (WebSocket)          (Athena/Demia/Rival)
         │                    │                    │
         ├──────────► cybercore-worker ◄──────────┤
         │                    │                    │
         ▼                    ▼                    ▼
    PostgreSQL            Redis              ClickHouse
    (OLTP+pgvector)      (缓存/队列)         (分析)
         │                                        │
         └──────────────► OSS ◄───────────────────┘
```

| 阶段 | 规模 | 架构形态 | 数据库 |
|------|------|----------|--------|

## 四、多租户与权限模型

### 4.1 租户层级

```
Platform（平台）
 └── Organization（学校 / 培训机构 / 教育局下属单位）
      └── Campus（校区，可选）
           └── Class（班级）
                └── User（学生 / 教师 / 校管）
```

### 4.2 隔离策略（按客户要求三档）

| 档位 | 模式 | 适用 | 实现 |
|------|------|------|------|
| **标准** | 逻辑隔离 | 绝大多数公立校 | 所有业务表含 `organization_id`；ORM 全局过滤 + PG **RLS** |
| **增强** | Schema 隔离 | 大型教育集团 | 每集团一 Schema，连接池按租户路由 |
| **旗舰** | 独立库实例 | 省会/直辖市教育局 | 独立 RDS；统一控制面 API |

　　**默认推荐标准档**：成本低、运维简单；RLS 防止应用层漏过滤。

### 4.3 身份与接入

| 场景 | 方案 |
|------|------|
| 学生/教师账号 | 手机号/学号 + 密码；班级邀请码入班 |
| 校级管理员 | 校管角色 + 2FA |
| 教育局统一身份 | **OAuth2 / SAML / 钉钉·企微·希沃 SSO** |
| 班级批量导入 | 模板 Excel → 异步任务 + 错误报告 |

### 4.4 权限（RBAC 示例）

| 角色 | 数据范围 | 典型操作 |
|------|----------|----------|
| `student` | 本人生涯、本班公开榜 | 学习、对局、Quest |
| `teacher` | 本班学生 | 开课、开赛、看板、布置 Quest |
| `school_admin` | 本校 | 教师/班级/学期配置 |
| `org_operator` | 跨校（教育局） | 报表、联赛、内容审核 |
| `platform_admin` | 全平台 | 赛制发布、租户开通 |

## 五、数据库分层与管理思路

### 5.1 核心原则：「一套权威 OLTP + 专用辅库」

　　不要把所有数据塞进一张「用户表」或一个 Redis。建议 **四类存储各司其职**：

| 类型 | 存储 | 存什么 | 管理要点 |
|------|------|--------|----------|
| **事务型（OLTP）** | PostgreSQL | 用户、班级、生涯、对局元数据、订单 | ACID、迁移、备份、RLS |
| **热状态** | Redis | 会话、房间、排行榜缓存、限流计数 | TTL、集群、不存唯一真相 |
| **分析型（OLAP）** | ClickHouse / PG 分析表 | 决策日志、行为事件、报表 | 异步写入、按月分区、可删可归档 |
| **非结构化** | OSS | 课件、快照 JSON、证书 PDF | 生命周期、CDN、访问签名 |

### 5.2 PostgreSQL：主库治理

**（1）Schema 组织（逻辑分域，物理同库）**

```
public          -- 租户、用户、班级
career          -- 生涯、XP、成就（或 public 前缀表）
academy         -- 课程、单元进度
arena           -- 对局、回合、决策索引
content         -- 内容版本、赛制配置元数据
ai              -- 会话摘要、复盘任务（不含原始对话长期存可选）
audit           -- 操作审计、登录日志
```

　　可用 **PostgreSQL Schema** 分域，仍享跨域事务（如「完成对局 + 记 XP」）。

**（2）迁移与版本**

- **Alembic**（Python）唯一迁移入口；禁止手工改生产表  
- 每条迁移可回滚；大表变更用 `CONCURRENTLY` 建索引  
- 配置数据（赛制 YAML）版本表：`game_configs(id, version, jsonb, published_at)`

**（3）连接与性能**

- **PgBouncer** 事务模式池化；API 与 Worker 分池  
- 读写分离：报表走 **只读副本**；写永远主库  
- 慢查询 > 200ms 告警；`pg_stat_statements` 定期复盘  

**（4）备份与恢复（RPO/RTO 建议）**

| 项目 | S2 建议 | S3 建议 |
|------|---------|---------|
| 全量备份 | 每日 | 每日 |
| WAL 连续归档 | 是 | 是 |
| RPO | ≤ 15 分钟 | ≤ 5 分钟 |
| RTO | ≤ 4 小时 | ≤ 1 小时 |
| 演练 | 每季度恢复演练 | 每月 |

**（5）保留与删除**

| 数据 | 热存储 | 温/archive | 删除策略 |
|------|--------|------------|----------|
| 账号/profile | 长期 | - | 用户申请注销后 30 天软删 → 匿名化 |
| 对局 decision_logs | 1 学年 | OSS 冷存 3 年 | 超期聚合后删明细 |
| AI 对话全文 | 90 天 | 仅保留摘要入 OLTP | 默认不用于训练外发 |
| 审计日志 | 1 年在线 | 3 年冷存 | 依法保留 |

### 5.3 分区（S2 起必做）

　　高增长表按时间或租户分区，避免单表过亿拖垮查询：

| 表 | 分区键 | 说明 |
|----|--------|------|
| `xp_events` | `created_at` 月分区 | 追加写入、历史可查 |
| `decision_logs` | `match_id` hash 或 `created_at` | 赛后分析主表 |
| `learning_records` | `created_at` | Apollo 学习轨迹 |
| `audit_logs` | `created_at` | 合规审计 |

　　PostgreSQL 16 **声明式分区**；旧分区 `DETACH` 后归档到 ClickHouse/OSS。

### 5.4 Redis：使用边界

| 用途 | Key 设计示例 | TTL |
|------|--------------|-----|
| 会话 | `sess:{session_id}` | 2h 滑动 |
| 对局房间 | `room:{match_id}:state` | 对局结束 +24h |
| 排行榜 | `lb:{org_id}:{season}:{scope}` | 5min；定时刷 PG 快照 |
| 限流 | `rl:{user_id}:{api}` | 1min |
| 分布式锁 | `lock:settle:{match_id}` | 30s |

　　**规则**：Redis 丢失可重建或可从 PG 恢复的数据才放 Redis；XP 账本以 **PG `xp_events` 为唯一真相**。

### 5.5 ClickHouse / 分析管道

```
OLTP (decision 完成)
    → 发 Domain Event (Kafka/Redis Stream 可选)
    → ETL Worker 批量写入 ClickHouse
    → Apollo 仪表盘 / 教师班级报告
```

　　S1 可用 **PG 分区表 + 物化视图** 代替 ClickHouse，降低运维；S2 再引入 CH。

### 5.6 对象存储（OSS）

| 路径模式 | 内容 |
|----------|------|
| `/{org_id}/content/{version}/` | 课件、视频转码产物 |
| `/{org_id}/matches/{match_id}/snapshot.json` | 对局完整快照（重放） |
| `/{org_id}/certs/{user_id}/` | 证书 PDF |
| `/{org_id}/exports/{job_id}/` | 班级成绩导出 |

　　桶策略：**私有读 + 签名 URL**；跨租户路径强制带 `org_id` 校验。

## 六、核心表域与分区策略

### 6.1 OLTP 核心实体（逻辑 ER 摘要）

```
organizations ──< classes ──< enrollments >── users
users 1──1 career_profiles
career_profiles 1──* xp_events (append-only)
career_profiles *──* knowledge_nodes (mastery)

game_configs ──< game_sessions ──< rounds ──< decision_logs (索引)
game_sessions *──* participants

content_bundles ──< learning_units ──< unit_progress
quest_templates ──< quest_instances

ai_debriefs, dialogue_logs (可选分区/脱敏)
```

### 6.2 关键设计决策

| 主题 | 决策 |
|------|------|
| **XP 账本** | `xp_events` 只 INSERT；`source_id` 唯一索引幂等 |
| **对局状态** | 权威在 PG `game_sessions.state_json` + Redis 热缓存；回合结束写不可变 `rounds` |
| **CyberCore 重放** | 存 `rules_version` + `random_seed` + 每回合输入 → Worker 可重算 |
| **排行榜** | 赛季快照表 `leaderboard_snapshots` 定时任务；实时榜 Redis |
| **多租户** | 所有表 `organization_id NOT NULL`；RLS：`current_setting('app.org_id')` |

### 6.3 索引策略（示例）

- `(organization_id, class_id, created_at DESC)` — 教师班级列表  
- `(career_id, created_at DESC)` — 生涯时间线  
- `(match_id, round_no)` — 复盘与 Ethos  
- `(user_id, source_type, source_id)` UNIQUE — XP 幂等

## 七、缓存、消息与实时对局

### 7.1 对局高峰（开学第一节课）

　　典型模式：1 校 40 班 × 40 人 ≈ 1600 人，其中 30% 同时进入对局 ≈ **500 WebSocket**。

| 组件 | 扩展方式 |
|------|----------|
| realtime-gw | K8s 多 Pod；Sticky Session 或 Redis 存房间路由 |
| api-service | 无状态 HPA；CPU 60% 扩容 |
| cybercore-worker | 队列消费；Worker 数 = 队列深度 |
| PostgreSQL | 连接池 + 写优化；避免长事务 |

### 7.2 消息队列（建议 S2 引入）

| 队列任务 | 优先级 | 消费者 |
|----------|--------|--------|
| `arena.settle` | 高 | cybercore-worker |
| `athena.debrief` | 中 | ai-orchestrator |
| `analytics.ingest` | 低 | etl-worker |
| `export.class_report` | 低 | report-worker |

## 八、AI 与内容数据

### 8.1 规模化下的 AI 治理

| 问题 | 策略 |
|------|------|
| 成本 | 按校配额；复盘异步；Demia 叙事可关；Rival 练习与排位分离 |
| 延迟 | 局内不调用大模型；仅规则层 POP；赛后队列生成复盘 |
| 隐私 | 对话脱敏进模型；可选 **私有化部署** 教育大模型（S3） |
| 质量 | 输出 JSON Schema 校验；幻觉不改变 Demia 数值 |

### 8.2 知识图谱与内容

- **发布态**：`content_releases` 表 + Git 源同步；学校可锁定教材版本  
- **向量**：按 `content_version` 分集合；升级时重建索引任务化  
- **赛制包**：`game_mode_packages` 垂直切片，对齐声明式框架目录结构

## 十、成本与容量规划（粗算）

　　以 **S2：50 万注册、5 万 DAU、峰值 5000 在线** 为例（单区域阿里云口径，仅量级）：

| 资源 | 规格思路 | 备注 |
|------|----------|------|
| PG RDS | 8～16 vCPU，500GB SSD，1 只读 | 分区 + 连接池 |
| Redis | 集群 8GB～16GB | 会话+房间+榜 |
| K8s 节点 | 4～8 台 4c8g（API+WS） | HPA |
| OSS | 5～20 TB（含视频） | 生命周期降冷 |
| ClickHouse | 2 节点（S2 末） | 可后置 |
| AI API | 按校包月 + 超额按次 | 最大变量 |

　　**优化顺序**：静态资源 CDN → 决策日志进 CH 而非 PG 无限膨胀 → AI 异步与模板化 → Reserved 实例。

## 十一、与现有 MVP 的衔接

| 现状 | 规模化动作 |
|------|------------|
| SQLite | **Alembic 迁 PostgreSQL**（P0 必做） |
| 前端 mock 数据 | OpenAPI 契约 + TanStack Query 接真实 API |
| 无 `organization_id` | 全表补租户字段 + RLS |
| 单机启动 | Docker Compose → 云 K8s 模板 |
| 声明式赛制 HTML 原型 | 迁入 `game_mode_packages` + CyberCore 配置库 |
