# 解耦声明式商业模拟框架总览

> **文档定位**：为商业模拟教育平台提供一套可扩展、可组合、声明式的赛事引擎架构设计。任何新的商赛模式无需修改核心代码，仅通过声明配置即可接入平台。
>
> **核心命题**：从"每种赛制写一套代码"走向"一种配置表达一种赛制"。
>
> **设计原则**：
> - **声明式优先**：赛制的规则、流程、界面、结算全部通过配置描述
> - **垂直解耦**：每种赛制是一个独立的"垂直切片"，不侵入其他赛制或核心引擎
> - **组合优于继承**：通过原子能力的组合构建复杂赛制，而非继承链
> - **状态外置**：对局状态与引擎逻辑分离，支持任意时刻的快照/恢复/重放
>
> **最后更新**：2026-05-16

## 一、框架设计哲学

### 1.1 从"硬编码"到"声明式"的范式转换

```
传统实现                                    声明式框架
┌─────────────────┐                        ┌─────────────────┐
│ 赛制A: 独立代码  │                        │  声明式内核引擎  │
│ 赛制B: 独立代码  │       ───→             │    (1套代码)     │
│ 赛制C: 独立代码  │                        │         ↑       │
│  ......          │                        │  ┌───────────┐  │
│  重复造轮子      │                        │  │ 赛制A配置  │  │
│  维护成本指数增长 │                        │  │ 赛制B配置  │  │
│                  │                        │  │ 赛制C配置  │  │
│                  │                        │  └───────────┘  │
└─────────────────┘                        └─────────────────┘
     N种赛制 = N套代码                          N种赛制 = 1套引擎 + N份配置
```

### 1.2 解耦的四个维度

| 维度 | 解耦前 | 解耦后 | 实现方式 |
|------|--------|--------|----------|
| **赛制与引擎** | 赛制逻辑写在引擎代码里 | 引擎读取赛制配置执行 | 声明式 DSL + 通用状态机 |
| **赛制与赛制** | 复制粘贴改代码出新赛制 | 各赛制独立配置包 | 垂直切片（Vertical Slice） |
| **状态与逻辑** | 状态散落在各函数中 | 状态统一托管，逻辑纯函数化 | 不可变状态树 + Reducer 模式 |
| **界面与规则** | 界面写死规则逻辑 | 界面通过 Schema 渲染 | 声明式 UI Schema |

### 1.3 声明式的三层含义

```
┌─────────────────────────────────────────┐
│  第一层：规则声明（Rule Declaration）      │
│  "什么条件下发生什么"用配置表达            │
│  例：当 round == 3 时开启间谍机制          │
├─────────────────────────────────────────┤
│  第二层：流程声明（Flow Declaration）      │
│  "对局如何推进"用状态机表达               │
│  例：SETUP → DECISION → SETTLE → RANKING │
├─────────────────────────────────────────┤
│  第三层：界面声明（UI Declaration）        │
│  "用户看到什么、能操作什么"用 Schema 表达  │
│  例：三栏布局 + 滑块组件 + 实时情报面板    │
└─────────────────────────────────────────┘
```

### 2.1 核心设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| **引擎与赛制关系** | 引擎通用，赛制配置化 | 新增赛制零代码，降低扩展门槛 |
| **状态存储方式** | 不可变状态树 + 事件溯源 | 支持任意时刻快照、重放、复盘 |
| **结算计算模式** | 纯函数式（输入→输出） | 可测试、可并行、确定性重放 |
| **界面渲染模式** | 声明式 Schema 驱动 | 一套渲染器适配所有赛制 |
| **扩展机制** | 能力原子组合 + 自定义 Hook | 覆盖99%场景，特殊需求通过 Hook 注入 |

## 三、声明式内核层

### 3.1 内核职责边界

```
CyberCore Kernel 负责：
✓ 解析 GameConfig，构建运行时规则对象
✓ 维护对局状态机，驱动生命周期流转
✓ 执行结算计算（调用配置的公式和原子能力）
✓ 管理事件总线，广播状态变更
✓ 提供快照/恢复接口

CyberCore Kernel 不负责：
✗ 具体赛制的业务规则（由配置描述）
✗ 用户认证与权限（由 Identity 服务处理）
✗ 界面渲染细节（由前端根据 UI Schema 渲染）
✗ 数据持久化（由 Repository 层处理）
```

### 3.2 状态机协议（FSM Protocol）

所有赛制共享同一套状态机骨架，具体流转由配置定义：

```yaml
# 状态机骨架（所有赛制通用）
fsm_protocol:
  version: "2.0"
  
  # 全局状态定义（每个对局必经）
  global_states:
    - CREATED        # 对局已创建
    - SETUP          # 参数配置、玩家加入
    - RUNNING        # 进行中
    - PAUSED         # 暂停（教师干预）
    - FINISHED       # 已结束
    - ARCHIVED       # 已归档
  
  # 运行时子状态（由具体赛制声明）
  runtime_states:
    - READY          # 等待开始
    - DECISION       # 决策阶段
    - REVIEW         # 决策审阅/确认
    - SETTLEMENT     # 结算中
    - INTERMISSION   # 回合间休息
    - EMERGENCY      # 紧急事件（可选）
  
  # 状态转换契约
  transitions:
    - from: CREATED
      to: SETUP
      trigger: host_start
      guard: player_count >= min_players
    
    - from: SETUP
      to: RUNNING
      trigger: host_begin
      guard: all_players_ready
    
    - from: RUNNING
      to: PAUSED
      trigger: host_pause
      
    - from: RUNNING
      to: FINISHED
      trigger: auto_finish
      guard: all_rounds_complete OR force_end
```

### 3.3 结算计算协议（Compute Protocol）

结算必须是**纯函数**：相同输入必定产生相同输出。

```typescript
// 结算函数签名（TypeScript 伪代码）
interface ComputeContext {
  gameConfig: GameConfig;        // 赛制配置（声明式规则）
  currentState: GameState;        // 当前完整状态树
  decisions: PlayerDecision[];    // 本轮所有玩家决策
  round: number;                  // 当前回合数
  randomSeed: string;             // 伪随机种子（保证可重放）
  timestamp: number;              // 结算时间戳
}

interface SettlementResult {
  newState: GameState;            // 新状态树（不可变）
  playerResults: PlayerResult[];  // 每个玩家的结果
  events: GameEvent[];            // 触发的游戏事件
  rankings: Ranking[];            // 当前排名
  logs: SettlementLog[];          // 详细计算日志（用于复盘）
}

type ComputeFunction = (ctx: ComputeContext) => SettlementResult;
```

### 3.4 事件总线协议（EventBus Protocol）

所有状态变更必须通过事件表达，事件是引擎与外部通信的唯一方式：

```yaml
# 核心事件类型（引擎层定义）
core_events:
  - GAME_CREATED
  - PLAYER_JOINED
  - STATE_CHANGED
  - DECISION_SUBMITTED
  - SETTLEMENT_COMPLETED
  - ROUND_ADVANCED
  - GAME_FINISHED
  - EMERGENCY_TRIGGERED

# 赛制自定义事件（在 GameConfig 中声明）
custom_events:
  - SPY_USED           # 间谍机制触发
  - ALLIANCE_FORMED    # 联盟建立
  - AUCTION_CLOSED     # 拍卖结束
  - CRISIS_OCCURRED    # 危机事件发生
```

## 四、能力原子库

能力原子是框架的"乐高积木"，每个原子是一个自包含、可配置、可组合的单元。

### 4.1 原子接口规范

```typescript
// 每个能力原子必须实现此接口
interface CapabilityAtom {
  id: string;                     // 唯一标识
  version: string;                // 语义化版本
  category: AtomCategory;         // 分类：mechanic | scoring | event | social
  
  // 配置 Schema（用于校验和表单生成）
  configSchema: JSONSchema;
  
  // 执行函数（纯函数）
  execute: (context: AtomContext) => AtomResult;
  
  // 声明式钩子（可选）
  hooks?: {
    onBeforeRound?: Hook;
    onAfterSettlement?: Hook;
    onPlayerDecision?: Hook;
  };
}
```

### 4.2 核心原子目录

#### 4.2.1 决策类原子（Decision Atoms）

| 原子ID | 名称 | 功能 | 配置示例 |
|--------|------|------|----------|
| `budget_allocate` | 预算分配 | 有限资源的多目标分配 | 预算总额、分配维度、约束条件 |
| `route_select` | 路线选择 | 从预设选项中选择策略路线 | 选项列表、互斥/多选、加成效果 |
| `city_occupy` | 城市占领 | 地图/市场中的位置选择 | 城市列表、容量限制、相邻规则 |
| `bid_sealed` | 密封投标 | 暗标出价机制 | 标的列表、保留价、胜出规则 |
| `bid_ascending` | 公开增价 | 英式拍卖 | 起拍价、加价幅度、超时规则 |
| `vote_majority` | 多数表决 | 集体决策投票 | 选项、票数规则、平局处理 |

#### 4.2.2 结算类原子（Settlement Atoms）

| 原子ID | 名称 | 功能 | 配置示例 |
|--------|------|------|----------|
| `softmax_share` | Softmax份额 | 基于投入计算市场份额 | 温度参数、衰减系数 |
| `linear_scoring` | 线性评分 | 多指标加权评分 | 指标列表、权重、归一化方式 |
| `ranking_elo` | ELO排名 | 动态实力评级 | K因子、初始分 |
| `budget_carry` | 预算结转 | 剩余资源跨回合处理 | 结转率、利息、损耗 |

#### 4.2.3 社会类原子（Social Atoms）

| 原子ID | 名称 | 功能 | 配置示例 |
|--------|------|------|----------|
| `alliance_form` | 联盟建立 | 玩家间临时合作 | 最大人数、共享属性、背叛惩罚 |
| `spy_reveal` | 间谍披露 | 信息获取机制 | 成本、披露范围、反间谍概率 |
| `negotiation_space` | 谈判空间 | 双边/多边协商 | 议题列表、时间限制、约束力 |
| `message_broadcast` | 广播消息 | 公开/定向信息 | 频道、可见范围、延迟 |

#### 4.2.4 事件类原子（Event Atoms）

| 原子ID | 名称 | 功能 | 配置示例 |
|--------|------|------|----------|
| `random_crisis` | 随机危机 | 概率触发的负面事件 | 事件池、触发概率、影响公式 |
| `timed_pressure` | 时间压力 | 倒计时约束 | 时长、预警阈值、超时惩罚 |
| `card_draw` | 卡片抽取 | 随机奖励/惩罚卡 | 卡池、抽取数、替换规则 |

### 6.3 快照与重放

```yaml
# 快照协议

  format_version: "2.0"

  full_snapshot:
    trigger: [round_end, manual, auto_interval]

  delta_snapshot:
    base: "full_snapshot_id"

  # 重放接口

    input: [initial_state, events[]]
    output: final_state
    deterministic: true   # 相同输入必定产生相同输出
```

## 九、扩展机制：自定义赛制开发指南

### 9.1 开发流程

```
Step 1: 能力盘点
  审视现有原子能力目录，列出所需原子
  如果所需原子已存在 → 进入 Step 3
  如果所需原子不存在 → 进入 Step 2

Step 2: 原子开发（需要代码能力）
  按照 CapabilityAtom 接口开发新原子
  提交到框架原子市场审核
  原子审核通过后对所有赛制可用

Step 3: 配置开发（无需代码）
  创建 game-mode-<id>/ 目录
  编写 main.yaml（规则、流程、原子组合）
  编写 ui-schema.yaml（界面声明）
  编写 i18n 文案

Step 4: 本地测试
  使用框架 CLI 工具加载配置
  运行模拟对局，验证结算正确性
  检查 UI Schema 渲染效果

Step 5: 注册上线
  打包为 zip 或推送到 Git
  在管理后台注册
  引擎自动校验并构建运行时
  教师即可在创建对局时选择
```

### 9.2 自定义 Hook（高级扩展）

当声明式配置无法表达特定逻辑时，可通过 Hook 注入自定义代码：

```typescript
// hooks/custom.ts 示例
import { HookContext, HookResult } from '@cybercore/engine';

export const hooks = {
  // 结算前钩子：可修改决策数据
  onBeforeSettlement: (ctx: HookContext): HookResult => {
    const { decisions, state } = ctx;
    
    // 自定义逻辑：联盟背叛检测
    const betrayals = detectBetrayals(state.social.alliances, decisions);
    
    return {
      modifiedDecisions: applyBetrayalPenalties(decisions, betrayals),
      events: generateBetrayalEvents(betrayals),
    };
  },
  
  // 状态变更钩子：可触发外部系统
  onStateChange: (ctx: HookContext): void => {
    const { newState, event } = ctx;
    
    // 自定义逻辑：当游戏结束时发送通知
    if (newState.lifecycle.current_state === 'FINISHED') {
      notifyExternalSystem('game.finished', {
        gameId: newState.meta.game_id,
        rankings: newState.computed.rankings,
      });
    }
  },
};
```

### 9.3 安全沙箱

自定义 Hook 在沙箱中执行，限制其能力：

```yaml
hook_sandbox:
  allowed_operations:
    - read_state              # 只读访问状态树
    - modify_decisions        # 修改决策（结算前）
    - emit_events             # 发射自定义事件
    - log                     # 写日志
    
  denied_operations:
    - network_request         # 禁止网络请求（通过引擎事件间接实现）
    - file_io                 # 禁止文件操作
    - setTimeout/setInterval  # 禁止异步定时器
    - eval                    # 禁止动态执行
    
  resource_limits:
    max_execution_time: 100   # 毫秒
    max_memory: 64            # MB
```

### 10.1 四阶段演进

| 阶段 | 目标 | 关键产出 | 时间估算 |
|------|------|----------|----------|
| **Phase 1: 内核铸造** | 构建声明式引擎核心 | FSM引擎、结算计算器、事件总线、状态管理 | 6周 |
| **Phase 2: 原子筑基** | 开发核心能力原子 | 15-20个标准原子、原子市场、测试套件 | 4周 |

### 10.2 技术债务规避

| 风险点 | 规避策略 |
|--------|----------|
| 配置过于复杂 | 提供可视化配置器，教师通过表单而非 YAML 配置 |
| 原子膨胀 | 原子必须通用，审查拒绝过具体的原子 |
| 性能瓶颈 | 结算计算保持纯函数，可并行化；状态树使用结构共享 |
| 版本兼容 | 严格的 semver 管理，运行时加载配置快照而非实时配置 |
| 安全风险 | Hook 沙箱 + 配置校验 + 运行时资源限制 |

### 10.3 成功度量

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 新增赛制开发周期 | < 3天 | 从需求到上线的时间 |
| 引擎代码变更频率 | < 1次/月 | 新增赛制是否需改引擎 |
| 配置化覆盖率 | > 95% | 赛制逻辑中配置 vs 代码的比例 |
| 状态重放一致性 | 100% | 相同事件流重放100次结果一致 |
| 教师自主配置率 | > 60% | 教师自行调整参数的比例 |

| **垂直切片（Vertical Slice）** | 按业务功能而非技术层次组织代码的结构方式 |
| **能力原子（Capability Atom）** | 可组合的最小 gameplay 功能单元 |
| **GameConfig** | 赛制的声明式配置文件，描述规则、流程、界面 |
| **FSM** | 有限状态机（Finite State Machine），管理对局生命周期 |
| **纯函数** | 相同输入必定产生相同输出，无副作用的函数 |
| **事件溯源** | 通过重放事件序列重建状态的持久化模式 |
| **UI Schema** | 描述界面结构和数据绑定的声明式格式 |
