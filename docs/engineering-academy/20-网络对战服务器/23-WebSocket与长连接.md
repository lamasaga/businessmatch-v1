# WebSocket 与长连接

> HTTP 是「问一句答一句」，WebSocket 是「建立一条持续对话的通道」。实时对战需要后者。

## 1. HTTP 的限制

普通 HTTP 请求：

- 客户端问，服务器答
- 答完就断开
- 服务器不能主动发消息给客户端

如果游戏状态每秒钟变化一次，用 HTTP 轮询（客户端不断问「有变化吗」）会非常浪费资源。

## 2. WebSocket 是什么

WebSocket 是一种在客户端和服务器之间建立**长连接**的协议。

特点：

- 连接建立后保持打开
- 双方可以随时发送消息
- 服务器可以主动推送给客户端
- 数据头很小，效率高

## 3. 在赛事引擎中的作用

| 场景 | 为什么用 WebSocket |
|------|-------------------|
| 实时价格更新 | 服务器每 tick 主动推送 |
| 玩家操作反馈 | 操作结果实时通知 |
| 比赛状态变化 | 开始、暂停、结束广播 |
| 聊天/通知 | 低延迟双向通信 |

## 4. 连接流程

```
客户端请求 WebSocket 连接
服务器接受，连接保持
客户端订阅某个房间 / 比赛
服务器把该房间的状态变化推送给客户端
比赛结束或客户端离开，连接关闭
```

## 5. 消息格式

WebSocket 消息通常用 JSON：

```json
{
  "type": "tick_update",
  "match_id": "abc123",
  "tick": 42,
  "state": {
    "prices": { "rice": 120 },
    "players": { ... }
  }
}
```

## 6. 连接管理

需要注意：

- 断线重连
- 心跳检测（确认对方还活着）
- 连接数上限
- 清理僵尸连接

## 7. 代码对应

- `webapp/backend/app/api/trading_ws.py`
- 前端：`webapp/frontend/src/stores/tradingStore.ts` 或类似文件

## 8. 与 AI 沟通示例

```
我要为新的实时赛制增加 WebSocket 状态推送。
需求：
- 玩家进入比赛房间后建立 WebSocket 连接
- 每 tick 服务器推送最新状态
- 支持断线重连并补发缺失 tick
- 连接关闭时清理资源
请使用 FastAPI WebSocket + 后端 scheduler 模式实现。
```
