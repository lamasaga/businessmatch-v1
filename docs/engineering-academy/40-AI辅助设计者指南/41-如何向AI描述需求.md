# 如何向 AI 描述需求

> 提示词（Prompt）质量决定 AI 输出质量。本文讲如何把模糊想法变成 AI 能执行的清晰指令。

## 1. 一个坏例子

❌ "帮我写个比赛功能。"

AI 不知道：

- 什么比赛？
- 回合制还是实时制？
- 涉及哪些表？
- 前端长什么样？
- 边界条件是什么？

## 2. 一个好例子

✅ "我要为 TechVenture 引擎增加一个『团队投票』功能。每个回合，团队成员投票决定下一回合的研发方向，多数票生效。需要：

1. 后端：新增 `tv_votes` 表，字段为 id、team_id、round、choice、created_at；
2. 后端：新增 POST /api/v1/techventure/{match_id}/vote 接口，校验每队每轮只能投一次；
3. 后端：回合推进时统计投票并应用结果；
4. 前端：学生端显示投票弹窗和当前投票结果；
5. 不要修改 arena 表。"

## 3. 描述需求的结构

```
背景：为什么要做这件事
范围：影响哪些模块
输入：用户提供什么
处理：系统做什么
输出：返回什么
约束：不能做什么、必须遵守的规则
验收标准：怎么算完成
```

## 4. 关键信息

| 信息 | 为什么重要 |
|------|-----------|
| Phase | 决定能做哪些事 |
| 域 | 防止跨域写入 |
| 引擎名 | 决定代码放哪里 |
| 新增/修改 | 改现有逻辑还是新建 |
| 接口路径 | 前后端对接 |
| 数据库表 | 持久化设计 |
| 校验规则 | 防止 AI 漏掉边界 |

## 5. 约束要前置

在需求开头就说清楚约束：

- 不要改 `arena` 表
- 不要改 frontend 路由
- 规则必须写在 YAML 里
- 必须用 SQLAlchemy 2.0

否则 AI 可能先写一大堆，然后再改。

## 6. 让 AI 先给方案再实现

对于复杂需求，可以先让 AI 给出方案：

```
请先给出实现方案，包括：
1. 修改哪些文件
2. 新增哪些文件
3. 数据库变更
4. API 设计
5. 可能的风险

方案确认后再写代码。
```

## 7. 示例模板

```
我要在 [Phase] 范围内为 [域/引擎] 增加 [功能]。

背景：
[为什么需要]

需求：
1. [后端] 新增/修改 [表/接口/逻辑]
2. [前端] 新增/修改 [页面/组件]
3. [配置] 修改 [YAML]

约束：
- 不修改 [表/路由/域]
- 遵循 [单写者/服务器权威/硬域边界]
- 使用 [技术栈]

验收：
- [可测试的点]
```
