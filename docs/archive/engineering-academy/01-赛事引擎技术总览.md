# 赛事引擎技术总览

> 给设计者的一页地图：平台里有哪些层、各管什么、以及「我想加一个新玩法」时要改哪里。

## 1. 为什么要分层

商业模拟平台里同时存在两类问题：

| 类型 | 例子 | 特点 |
|------|------|------|
| **生命周期问题** | 报名、分组、开始、结算、颁奖 | 通用，和具体玩法无关 |
| **玩法规则问题** | 供需曲线、库存、交易撮合、AI 决策 | 每个赛制都不一样 |

如果不分开，加一个赛制就要改报名、改结算、改界面、改数据库，越往后越乱。所以平台拆成两层：

- **Arena（赛场）**：只管「这场比赛从创建到结束」的流程。
- **Engine（引擎）**：只管「这个玩法的规则怎么算」。

## 2. 三层结构

```
┌─────────────────────────────────────┐
│  前端（学生端 / 组织者端）            │
│  展示状态、收集操作、播放动画         │
├─────────────────────────────────────┤
│  API 层（FastAPI）                   │
│  路由、鉴权、参数校验、调用业务逻辑   │
├─────────────────────────────────────┤
│  Arena 域                            │
│  比赛创建、报名、房间、回合推进、结算  │
├─────────────────────────────────────┤
│  Engine 域                           │
│  配置读取、状态计算、AI 决策、分数    │
├─────────────────────────────────────┤
│  数据库（SQLite）                    │
│  持久化状态                          │
└─────────────────────────────────────┘
```

## 3. Arena 负责什么

- 创建比赛（practice / official）
- 生成房间码、管理参赛者
- 推进回合 / tick（对于回合制和 RTS 有区别，见下方）
- 调用 Engine 进行结算
- 记录结果、分发奖励（通过 Career 域）

**关键文件**：

- `webapp/backend/app/domains/arena/models.py`
- `webapp/backend/app/api/competitions.py`
- `webapp/backend/app/api/practice.py`
- `webapp/backend/app/domains/arena/ARCHITECTURE.md`

## 4. Engine 负责什么

- 读取 YAML 配置（轮数、城市、商品、参数）
- 维护运行时状态（库存、价格、分数、AI 状态）
- 执行玩家提交的操作
- 计算每轮 / 每 tick 的更新
- 返回给 Arena 一个「结算快照」

**关键文件**：

- `webapp/backend/content/game-configs/*.yaml`
- `webapp/backend/app/games/trading/`（浮生记 RTS）
- `webapp/backend/app/games/techventure/`（TechVenture 回合制）

## 5. 配置驱动：YAML 是什么角色

引擎的规则不写在 Python 代码里，而写在 YAML 文件里。原因：

1. **策划可改**：想调一个参数，改 YAML 即可，不用重新部署后端。
2. **可扩展**：新赛制可以新增 YAML，不污染老代码。
3. **可验证**：加载 YAML 时可以做 schema 校验，防止手滑写错。

一个 YAML 通常包含：

```yaml
engine: trading
name: 浮生记基础版
rounds: 10
cities: [城市A, 城市B]
products:
  - id: rice
    name: 大米
    base_price: 100
rules:
  - type: demand_curve
    params: ...
```

## 6. 回合制 vs 实时制

| 维度 | 回合制（TechVenture） | 实时制 / RTS（浮生记） |
|------|----------------------|----------------------|
| 推进方式 | 等所有人类玩家提交后统一推进 | 调度器按固定间隔自动 tick |
| 操作时机 | 每回合内任意时间提交 | 在 tick 边界前提交指令 |
| AI 行为 | 回合结束时统一决策 | 每个 tick 都可能决策 |
| 前端体验 | 表单、弹窗、回合总结 | 实时面板、倒计时、动画 |
| 核心文件 | `games/techventure/engine.py` | `games/trading/rts_scheduler.py` |

**RTS 关键原则：调度器单写者**

只有 `rts_scheduler.py` 里的 `maybe_advance_rts` 能推进 tick。HTTP 接口只读不写，玩家操作先进入队列，下一个 tick 再结算。这是为了保证状态一致性。

## 7. 新增一个赛制要动哪里

以「我要做一个拍卖赛制」为例：

1. **写 YAML**：`content/game-configs/auction-demo.yaml`
2. **建 Engine 目录**：`app/games/auction/` 下放 `engine.py`、`models.py`、`ai.py`
3. **在 Arena 注册**：让 `get_game_config()` 和 `merged_match_config()` 能识别新引擎
4. **加 API**：如果需要新的操作类型，加 `api/auction.py` 并在 `main.py` 挂载
5. **前端页面**：学生端加比赛界面，组织者端加控制台
6. **文档**：更新 `03-ENGINEERING.md`、补 ADR（如果涉及架构选型）

## 8. 给 AI 描述需求时的关键词

| 你想说的 | 可以跟 AI 说的关键词 |
|---------|-------------------|
| 加一个玩法 | "新增 game engine，不要动 arena 表" |
| 调整规则参数 | "修改 YAML game-config，不是改代码" |
| 实时比赛 | "RTS scheduler single-writer" |
| 多人同屏刷新 | "WebSocket broadcast after commit" |
| 防止作弊 | "server authoritative, validate inputs" |
| AI 玩家 | "add AI agent to engine" |

## 9. 常见误区

- ❌ "我把规则写在前端了" → 规则必须在后端 / YAML，前端只展示。
- ❌ "我直接改了 Arena 的数据库表" → 跨域写入违反硬域边界。
- ❌ "HTTP 接口里推进了 tick" → RTS 必须由调度器推进。
- ❌ "我在 SQLAlchemy 模型里算分" → 算分是 Engine 的职责。
