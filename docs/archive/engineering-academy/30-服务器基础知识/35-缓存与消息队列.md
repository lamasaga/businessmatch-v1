# 缓存与消息队列

> 当用户变多、请求变慢时，就需要缓存和消息队列。本文讲它们是什么、什么时候用。

## 1. 缓存（Cache）

缓存是把常用数据放到更快的存储里，下次用的时候直接拿。

### 为什么用缓存

数据库查询可能比内存慢几十倍。如果某个数据被频繁查询：

- 第一次从数据库读，存入缓存
- 后面从缓存读，速度快很多

### 常见缓存

| 类型 | 例子 |
|------|------|
| 内存缓存 | 程序内变量、LRUCache |
| 分布式缓存 | Redis、Memcached |
| 浏览器缓存 | 前端静态资源 |
| CDN | 图片、JS、CSS 加速 |

### 本项目现状

当前项目规模不大，主要靠单进程 + SQLite，缓存不是核心问题。后续扩展时可能引入 Redis。

### 缓存注意事项

- 缓存数据可能过期
- 重要数据最终要以数据库为准
- 更新数据时要让缓存失效

## 2. 消息队列（Message Queue）

消息队列是「先存起来，慢慢处理」的机制。

### 为什么用消息队列

- 削峰：大量请求来时先排队，慢慢处理
- 解耦：发送方和接收方不直接依赖
- 可靠：消息不会丢

### 例子

比赛结束后要发奖励、发通知、更新排行榜。这些不需要立刻完成，可以放进队列，后台慢慢处理。

### 常见消息队列

| 工具 | 特点 |
|------|------|
| Redis + Celery | 简单，Python 生态常用 |
| RabbitMQ | 功能丰富 |
| Kafka | 高吞吐，大数据场景 |

### 本项目现状

当前用调度器直接处理。后续大规模时可能引入任务队列。

## 3. 与 AI 沟通关键词

| 你想说的 | 关键词 |
|---------|--------|
| 查询太慢 | "add caching, Redis cache" |
| 大量请求处理不过来 | "message queue, async task" |
| 后台慢慢算 | "background job, worker" |
| 削峰 | "rate limiting, queue throttling" |

## 4. 与 AI 沟通示例

```
比赛结束后有很多后续操作（发奖励、更新排行榜、发通知），
我不想让前端一直等。
请设计一个后台任务队列：
- 比赛结束时把任务放入队列
- 后台 worker 依次处理
- 处理失败可重试
- 提供状态查询接口
```
