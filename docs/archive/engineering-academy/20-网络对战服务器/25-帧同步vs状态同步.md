# 帧同步 vs 状态同步

> 多人游戏让所有人看到一致画面有两种思路。本项目用状态同步，但你需要知道另一种方案，才能与 AI 讨论清楚。

## 1. 状态同步（State Synchronization）

服务器计算完整状态，然后广播给客户端。

```
服务器：计算 tick 42 的状态 → 广播给所有客户端
客户端：收到 → 直接显示
```

优点：

- 客户端简单
- 防作弊容易
- 适合逻辑复杂的商业模拟

缺点：

- 服务器压力大
- 带宽消耗大

## 2. 帧同步（Lockstep / Frame Sync）

服务器只转发玩家输入，客户端各自根据输入计算状态。

```
玩家 A 操作 → 服务器 → 转发给 B
玩家 B 操作 → 服务器 → 转发给 A
客户端 A：根据 A 和 B 的输入计算状态
客户端 B：根据 A 和 B 的输入计算状态
```

优点：

- 服务器压力小
- 带宽小

缺点：

- 客户端逻辑必须完全一致
- 浮点数运算要同步处理
- 防作弊困难
- 延迟敏感

## 3. 对比

| 维度 | 状态同步 | 帧同步 |
|------|---------|--------|
| 服务器压力 | 大 | 小 |
| 带宽 | 大 | 小 |
| 客户端复杂度 | 低 | 高 |
| 防作弊 | 容易 | 难 |
| 延迟容忍 | 较高 | 低 |
| 适用 | 商业模拟、MOBA | RTS、格斗游戏 |

## 4. 本项目的选择

商识唯智的赛事引擎以**状态同步**为主。原因：

- 商业模拟逻辑复杂，客户端重算容易出错
- 需要服务器权威防止作弊
- 对延迟要求不如格斗游戏那么高
- 方便做回放和审计

浮生记 RTS 也是状态同步：调度器计算状态后通过 WebSocket 广播。

## 5. 什么时候考虑帧同步

如果未来要做：

- 高频操作对战
- 极低延迟需求
- 大规模同屏单位

才考虑帧同步或混合方案。

## 6. 与 AI 沟通关键词

| 你想说的 | 关键词 |
|---------|--------|
| 服务器算完再发 | "state synchronization, server authoritative" |
| 客户端各自算 | "frame lockstep, deterministic simulation" |
| 我怕客户端作弊 | "use state sync to prevent client cheating" |
| 服务器压力太大 | "consider delta compression in state sync" |
