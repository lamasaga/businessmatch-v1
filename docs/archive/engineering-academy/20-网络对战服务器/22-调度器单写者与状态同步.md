# 调度器单写者与状态同步

> 浮生记 RTS 的核心设计：只有一个地方能推进游戏时间，HTTP 只读不写。本文解释为什么这样设计，以及它如何工作。

## 1. 问题背景

如果多个 HTTP 请求同时修改游戏状态，会发生什么？

- 两个玩家同时下单，库存可能算错
- 一个 tick 内多次推进，状态跳跃
- 不同玩家看到的价格不一致
- 数据库出现竞争条件（race condition）

解决思路：**只允许一个写入者**。

## 2. 什么是调度器单写者

在本项目 RTS 中：

- **HTTP `/state`**：只读，查询当前状态，不推进。
- **HTTP `/actions`**：接收玩家指令，放入队列，不立即结算。
- **调度器（Scheduler）**：定时运行 `maybe_advance_rts`，依次处理队列、推进 tick、写数据库、广播新状态。

```
玩家 A 下单 → /actions → 进入队列
玩家 B 下单 → /actions → 进入队列
调度器 tick → 处理 A 的订单 → 处理 B 的订单 → 计算新状态 → 写入数据库 → 广播
```

## 3. 为什么 HTTP 不能推进

HTTP 是无状态的，每个请求独立。如果让 HTTP 推进 tick：

- 玩家 A 请求时推进了一次
- 玩家 B 请求时可能又推进一次
- 两者之间的时间差难以控制

调度器是后台任务，按固定间隔（如每秒）执行，节奏稳定。

## 4. 状态同步流程

```
1. 调度器推进 tick
2. 计算新状态
3. 写入数据库（commit）
4. 通过 WebSocket 广播给所有客户端
5. 客户端收到后更新界面
```

注意：**commit 完成前不广播**。这是为了保证客户端收到的是已经确认的状态，而不是中间态。

## 5. 与回合制的区别

| 维度 | 回合制 | RTS |
|------|--------|-----|
| 推进触发 | 玩家全部提交后 | 调度器定时 |
| 写入者 | `practice_flow.py` 推进 | `rts_scheduler.py` 推进 |
| 事务 | 一个事务包含人类+AI+推进 | 每个 tick 一个事务 |
| 前端刷新 | 回合总结时 | 每 tick |

## 6. 代码对应

- `webapp/backend/app/games/trading/rts_scheduler.py`
- `webapp/backend/app/api/trading.py`（只读）
- `webapp/backend/app/api/trading_ws.py`（WebSocket 广播）

## 7. 与 AI 沟通关键词

| 你想说的 | 关键词 |
|---------|--------|
| 防止多请求冲突 | "single writer, scheduler owns state mutation" |
| HTTP 只读 | "HTTP endpoints are read-only for game state" |
| 操作排队 | "queue actions, process on next tick" |
| 先提交再广播 | "commit before broadcast" |

## 8. 常见误区

- ❌ "我在 /actions 里直接改数据库" → 应该只入队。
- ❌ "客户端自己算 tick" → 客户端只展示，不算。
- ❌ "广播在 commit 前发" → 可能广播失败状态。
