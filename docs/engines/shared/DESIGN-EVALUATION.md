# 赛事部分设计评估与提升建议

> **评估范围**：Arena 域下的 FST（浮生记）、TECH（创想大赢家）、OPS（生产经营销售赛）三套赛事引擎的前后端呈现、美术资源与可持续开发路径
> **评估视角**：技术栈、2D 美术资源、后续开发、整体 UI 呈现
> **版本**：1.0.0
> **最后更新**：2026-06-14

---

## 1. 概述

当前赛事部分已形成 **FST（即时物流套利）+ TECH（回合制属性竞争）+ OPS（回合制运营 + 竞价）** 三引擎并行的格局：

- **FST**：后端 RTS 调度器 + WebSocket 单写者模式成熟，前端当前以 React + SVG 地图实现，Phaser 场景处于 B 阶段占位。
- **TECH**：前后端完整度最高，拥有参赛端、组织端控场、大屏投影、评委视角四重视角。
- **OPS**：近期完成前后端对接，学生端局内组件（定位、决策、拍卖、报表、排名）已落地，组织端控场页已可用。

整体架构符合 `02-ARCHITECTURE.md` 与 `domains/arena/ARCHITECTURE.md` 的分层约定：引擎 / 配置 ID / `match_kind` 三层解耦。但在**视觉一致性、数据可视化、组件复用、美术资产、性能体验**上仍有明显提升空间。

## 2. 技术栈评估

### 2.1 当前技术栈

| 层级 | 学生端 | 组织者端 | 后端 |
|------|--------|----------|------|
| 框架 | React 19 + Vite 8 | React + Vite | FastAPI + SQLAlchemy 2 |
| 状态管理 | Zustand 5 | Zustand | — |
| 样式 | Tailwind CSS 3.4 | Tailwind CSS 3.4 | — |
| 图标 | lucide-react | lucide-react | — |
| 实时通信 | FST 用 WebSocket；TECH/OPS 用 HTTP 轮询 | HTTP 轮询 | WebSocket hub（仅 FST） |
| 图表 | 无 | 无 | — |
| 动画 | CSS 动画为主 | CSS 动画为主 | — |
| 地图 | SVG + 原生 img（`/assets/fushengji/...`） | — | — |

### 2.2 优势

1. **栈统一、学习成本低**：双前端共用 React + Tailwind + Zustand + lucide-react，人员可在两项目间快速切换。
2. **配置驱动**：三引擎均通过 `content/game-configs/*.yaml` 定义规则，新增赛事/地区时多数情况只需新增 YAML，符合 Arena 架构规范。
3. **RTS 单写者模式可靠**：FST 的 `rts_scheduler.py` 与行锁设计已验证，40 人局 tick 延迟 < 100ms。
4. **前后端类型约定清晰**：`frontend/src/types/` 下按引擎拆分类型文件，接口变更可追溯。

### 2.3 问题与提升空间

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 1 | **无 UI 组件库**，所有表单、表格、弹窗手写 Tailwind | 重复代码多、一致性难保证、新增交互成本高 | 引入 Headless UI 层（如 Radix UI / Ariakit）或轻量组件库（shadcn/ui），优先统一 `<Input>`、`<Button>`、`<Select>`、`<Dialog>`、`<Tabs>` |
| 2 | **无图表库**，排名、趋势、份额全部用表格展示 | 学生难以快速感知趋势；组织者大屏信息密度低 | 引入 `recharts` 或 `echarts-for-react`，优先做：① 净资产/排名趋势折线图；② 市场份额饼图/堆叠条形图；③ 城市需求热力图 |
| 3 | **双前端独立**，组件/工具函数无法直接复用 | 相同交互（房间码复制、排行榜、加载态）各自实现，风格略不一致 | 抽取 `@bizsim/shared-ui` 包或至少建立 `packages/ui` monorepo 子包；短期可用 relative symlink / git submodule 过渡 |
| 4 | **实时通信未统一**：FST 用 WS，TECH/OPS 用轮询 | 轮询在课堂弱网/多 Tab 下产生冗余请求；OPS 拍卖阶段延迟感明显 | OPS/TECH 的关键阶段（拍卖倒计时、轮次切换、结算完成）接入 WebSocket 推送；保留 HTTP 轮询作为 fallback |
| 5 | **无动画/过渡库**，页面切换、数据更新较生硬 | 结算结果突然出现，学生缺少心理准备；大屏缺少仪式感 | 引入 `framer-motion` 做列表进入/退出、数字滚动、结算弹窗、拍卖锤动画 |
| 6 | **表单校验前置于前端不足**：OPS 决策表仅后端校验，错误反馈延迟 | 学生提交后才知超支，体验差 | 在 `DecisionForm` 中复用后端校验逻辑（或抽公共校验函数），实现即时禁用提交按钮 + 红色提示 |
| 7 | **移动端适配未系统验证**：当前布局以桌面/平板为主 | 学生用手机加入时，拍卖、地图、表格操作困难 | 为赛事入口页增加移动优先断点；地图在窄屏下切换为城市列表 + 卡片 |

### 3.2 优势

1. FST 地图已有城市标记、商队移动、事件的基础视觉语言，暖白 + 深灰剪影风格与暗色 UI 形成对比，辨识度高。

### 3.3 缺口与提升建议

| # | 缺口 | 影响 | 建议 |
|---|------|------|------|
| 1 | **城市图标不全**：FST 长三角六城仅有南京、南通、上海有 SVG | 其他城市 fallback 为默认图标，地图辨识度下降 | 补齐杭州、苏州、无锡、宁波等城市 SVG；统一 48×48 风格（剪影 + 地标轮廓） |
| 2 | **OPS 素材几乎空白**：PRD-OPS §8.5 列出的品类图标、城市图标、角色头像、奖杯奖牌、拍卖锤均无 | 产品定位、拍卖、结算页全是文字，教育仪式感弱 | 按 PRD-OPS 清单分批补齐：① 3C/快消/家居品类插画；② 一线/新一线/二线/三线城市徽章；③ CEO/CFO/CMO/COO 角色头像；④ 奖杯/奖牌/拍卖锤/倒计时动效 |
| 3 | **商品图标缺失**：FST 当前用表格文字展示商品，无视觉符号 | 学生记忆成本高，大屏缺少直观性 | 为粮食、家电、汽车、奢侈品等 10 种商品设计 24×24/32×32 图标；在表格与地图弹窗中引用 |
| 4 | **车辆与商队视觉单一**：仅 passenger_car / luxury，无 van/truck 差异化图标 | 购车决策缺少视觉反馈 | 设计小货车（van）与大卡车（truck）两款车型 SVG；`FushengjiFleetMarker` 根据车辆类型切换图标 |
| 5 | **事件/新闻视觉弱**：事件仅在配置中以文字存在，无弹窗/横幅动效 | 市场事件冲击力不足 | 为消费降级、原材料涨价、政策补贴、丰收、拥堵等事件设计横幅插画与 Toast 动效 |
| 6 | **无统一插画系统**：暗色 UI + 金色主色，但插画风格未统一 | 各引擎视觉调性不一致 | 制定「商识唯智插画规范」：主色 `#d4a853`、辅色 `#2dd4a0`、线宽 1.5px、圆角风格、人物几何化 |
| 7 | **缺少成就/徽章体系**：PRD 提到特殊奖项，但无视觉资产 | 结算页缺少荣誉感 | 设计最佳产品、最佳交易、最佳运营、最佳路线等奖章；与 Career 成就系统共用 |
| 8 | **大屏投影专用素材缺失**：TechVentureScreen 仅用 Emoji 奖牌 | 课堂/比赛现场投影时不够正式 | 制作 Top3 领奖台、金牌/银牌/铜牌矢量图、动态背景粒子 |

## 4. 整体 UI 呈现评估

### 4.1 当前一致性好的一面

- **暗色主题统一**：`#0a0a0b` 背景 + `#d4a853` 主色 + `#2dd4a0` 成功色，贯穿双前端。
- **玻璃拟态卡片**：`.glass-card` 组件在 FST、TECH、OPS 学生端均有使用，形成平台感。
- **字体与数字**：`Inter` + `JetBrains Mono` 搭配，金额/排名使用等宽数字。

### 4.2 不一致与体验短板

| # | 问题 | 具体表现 | 建议 |
|---|------|----------|------|
| 1 | **组织者端与学生端色调分裂** | 组织者端使用 `bg-gray-800/900/950`（偏冷灰），学生端使用 `bg-background-secondary`（偏暖黑） | 统一组织者端色板至与学生端一致的 `--background`、`--background-card`、`--foreground-muted` |
| 2 | **原生输入框未封装** | `input[type=number]`、`textarea`、`select` 在 OPS/TechVentureControl 中样式各异 | 封装 `<NumberInput>`、`<Slider>`、`<CitySelector>`，统一聚焦态、错误态、禁用态 |
| 3 | **数据密度高但可视化少** | OPS 财务报表为纯文字列表；TECH 声量/BQI 只有数字；FST 库存/排行用表格 | 增加迷你趋势图、进度环、雷达图；让学生一眼看到「自己在哪里」 |
| 4 | **缺少阶段感与仪式感** | 轮次切换、结算、拍卖成交、比赛结束都是页面元素替换，缺少过渡 | ① 轮次切换用全屏倒计时；② 结算用「新闻播报」弹窗；③ 拍卖成交用锤击动画 + 横幅；④ 结束用领奖台动画 |
| 5 | **新手引导缺失** | 首次进入的学生直接看到决策表单，无教学提示 | 增加首次进入的「新手模式」：高亮关键字段、工具提示、示例决策；可在 YAML 中配置 `tutorial_steps` |
| 6 | **错误与空状态不统一** | 各页面自定义 loading/error 样式，部分仅显示文字 | 统一 `<LoadingState>`、`<EmptyState>`、`<ErrorState>` 组件 |
| 7 | **OPS 拍卖大厅实时感弱** | 当前为输入框出价，无倒计时、无人数提示、无出价历史 | 增加倒计时条、最近出价滚动、出价音效开关、当前领先高亮 |
| 8 | **排行榜缺少「我的位置」** | TECH/OPS 仅高亮自己行，长列表时不易定位 | 固定显示「我的排名」卡片 + 滚动到当前位置按钮 |
| 9 | **FST 地图在窄屏下不可用** | 地图 + 表格 + 操作区三栏在 13 寸以下笔记本/平板上拥挤 | 增加「地图模式 / 列表模式」切换；移动端默认列表 |
| 10 | **大屏投影页信息层次弱** | TechVentureScreen Top3 与 Top10 视觉重量接近 | 强化 Top3（放大头像/路线插画、动态粒子），Top10 收为紧凑列表 |

### 4.3 重点页面改进建议

#### 4.3.1 OPS 学生端（`OpsPlayPage` / `OpsLobbyPage`）

- **大厅页**：增加产品定位进度环、队伍头像、等待动画；房间码增加一键复制 + 二维码分享。
- **决策页**：
  - 用滑块替代数字输入（生产量、营销、研发）。
  - 城市选择使用地图 + 卡片双模式。
  - 增加「预算仪表盘」，实时显示现金/支出/剩余。
  - 增加「本轮建议」占位（未来接 AI 助教）。
- **拍卖页**：改为拍卖大厅布局，左侧拍品列表 + 中央当前拍品大图 + 右侧出价历史。
- **报表页**：损益表增加红绿灯标记；资产负债表增加资产构成饼图；增加「销量漏斗」可视化。
- **结算页**：前三名突出展示，增加奖项徽章与 XP/金币到账动画。

#### 4.3.2 TECH 学生端（`TechVenturePlayPage`）

- **战略选择**：四路线卡片增加插画与简短口号动画。
- **资金分配**：Fit/Show 按城投入时，用城市小卡片 + 滑块组合，减少纵向滚动。
- **反馈区**：KPI 卡片增加与上轮的 delta 箭头；BQI 因素用图标 + 颜色区分正负。
- **新闻面板**：结算后自动滚动新闻，增加「头条」与普通新闻的视觉区分。

#### 4.3.3 FST 学生端（`TradingRTSView`）

- **地图与价格联动**：点击城市后，价格面板与该城市联动，当前城市高亮。
- **在途状态可视化**：`FushengjiFleetMarker` 增加到达倒计时与路径进度条。
- **操作反馈**：提交 action 后，在地图上显示「正在前往 XX」「已买入 XX」等临时提示。
- **事件弹窗**：事件触发时全屏或半屏弹窗，配插画与音效。

#### 4.3.4 组织者端

- **统一布局**：所有控场页采用「顶部粘性操作栏 + 统计卡片区 + 详情区」三件套。
- **数据看板**：
  - OPS 控场增加「净资产趋势图」「市场份额堆叠图」。
  - TECH 控场增加「路线分布饼图」「城市投入热力图」。
  - FST 控场增加「tick 进度条」「资产分布」「实时交易流水」。
- **大屏模式**：为 OPS 增加 `/events/:id/ops/screen` 大屏路由，参考 TechVentureScreen。
- **评委视角**：OPS/FST 可复用 TechVentureJudge 模式，提供逐队展开与对比。

### 5.3 不建议现在做的

- **更换主技术栈**（如从 React 换 Vue/Svelte）：当前栈统一且团队已熟悉，迁移收益不抵成本。
- **引入重型 UI 框架**（如 Ant Design / Material UI）：与现有暗色玻璃拟态风格冲突，定制成本高。
- **立即做 3D 地图或复杂动画**：Phase A 以可玩闭环与教学效果为主，3D 属于 C/D 阶段愿景。

## 6. 风险与注意事项

1. **双前端共享组件时避免破坏现有路由与构建**：建议先在一个前端内封装 `ui/` 目录，稳定后再提取为共享包。
2. **图表库体积**：`recharts` 约 80KB gzip，`echarts` 更大。若仅做简单图表，可考虑 `chart.js` + `react-chartjs-2` 或自研 SVG 图表。
3. **WebSocket 扩展**：统一 WS 层时需注意 FST 的调度器单写者约束，避免其他引擎引入新的写者。
4. **美术资产迭代**：SVG 图标优先，确保可缩放、可改色；避免早期使用位图导致后期替换困难。
5. **移动端适配**：赛事核心操作复杂，移动端以「查看 + 简单确认」为主，不宜复刻完整决策界面。

## 7. 结论

当前赛事部分在**架构正确性、后端稳定性、规则完整性**上已经具备 Phase A 所需的骨架。最大的提升空间集中在：

1. **统一 UI 组件与可视化**：用组件库 + 图表库把表格数据转化为可感知的趋势与对比。
2. **补齐 2D 美术资产**：城市、商品、路线、角色、奖杯、事件插画是提升教育仪式感的关键。
3. **强化阶段感与新手引导**：结算、拍卖、轮次切换需要更明确的视觉与动效反馈。
4. **统一双前端风格与通信模式**：减少重复实现，提升组织者端与学生端的一致性。

建议按「P0 组件/图表/图标 → P1 色板/拍卖/大屏 → P2 新手引导/排行榜」的顺序推进，保持 Phase A 边界，将 Phaser、共享包、复杂成就体系留给 B 阶段。
