# ADR-002: 模块化单体与单库单进程

**日期**：2026-05-21  
**状态**：已采纳  
**触发**：M4

---

## 上下文

　　平台有**学生端**、**组织者端**、多种赛制（浮生记、TechVenture 等）。常见诱惑是为每端或每赛制单独起后端、单独建 SQLite，以降低「耦合感」。但这会带来部署、事务、账号与对局状态分裂，MVP 阶段运维和调试成本陡增。

---

## 决策

　　采用**模块化单体（Modular Monolith）**：

- **一个** FastAPI 进程（`webapp/backend`），路由挂载在 `/api/v1`
- **一个** SQLite 数据库（开发/演示；规模化目标为 PostgreSQL，仍**单库**）
- 按**域**分包（`domains/arena`、`domains/career`、`games/trading`…），而非按客户端拆服务

**落地位置**：

- 入口：`webapp/backend/app/main.py`
- 配置：`webapp/docker-compose.yml`（前端可多个容器，后端一个）
- 文档：`02-ARCHITECTURE.md` §高层架构 · `03-ENGINEERING.md` §一 后端 API 全表

---

## 考虑过的方案

| 方案 | 优点 | 缺点 | 未采用原因 |
|------|------|------|------------|
| 组织者独立后端 + 独立库 | 感觉「解耦」 | 双倍部署；房间码/对局跨库同步难 | MVP 不需要 |
| 每赛制一个微服务 | 隔离崩溃 | 本地开发要起 N 个进程；事务跨服务难 | Phase A 过度设计 |
| **单 API + 单库 + 域分包（已采纳）** | 本地一条命令启动；事务简单 | 单体变大后需纪律分包 | 与当前团队与 Phase A 匹配 |

---

## 后果

### 正面

- 学生/组织者/练习/正式赛共用同一套用户与 `competition_events`
- Docker Compose 已按「一后端 + 双前端」验证

### 负面 / 代价

- 后端仓库体积会变大；须靠**域边界**（ADR-003）防止变成大泥球
- SQLite 并发与迁移有限；Phase B 计划迁 PG（见 `04-`），但**不拆库**

### 给初学者的操作提示

- **可以做的**：在 `app/api/` 加路由，在 `domains/` 或 `games/` 写业务；用 `docker compose up` 起全栈
- **不要做的**：新建 `organizer-backend/` 或第二个 `.db` 文件给组织者专用
- **相关阅读**：`02-ARCHITECTURE.md` §高层架构 · `03-ENGINEERING.md` §一 后端 API 全表 · `webapp/README.md`
