# ADR-005: 浮生记 RTS 调度器单写者

**日期**：2026-05-21  
**状态**：已采纳  
**触发**：M4、M5

---

## 上下文

　　浮生记 **RTS 版**（`trading-v2-rts`）需要定时推进游戏 tick，并向所有客户端推送状态。若在 HTTP `GET /state` 或 `POST /actions` 里顺便推进 tick，会出现：并发请求双写、WebSocket 在 DB commit 前广播「结束」、调试时无法区分「读状态」与「改状态」。

---

## 决策

　　采用**调度器单写者（Single Writer）**模式：

| 职责 | 负责方 | 行为 |
|------|--------|------|
| 推进 tick | **仅** `games/trading/rts_scheduler.py` → `maybe_advance_rts` | 应用 lifespan 启动/恢复 |
| 读状态 | `api/trading.py` / handlers | **只读**，不调用推进函数 |
| 玩家操作 | `POST /actions` | 排队指令，**下次 tick** 结算，不即时推进 |
| 推送 | `rts_ws.py` | **`commit` 之后**再 `broadcast` |

　　回合制练习局另由 `practice_flow.py` 在人类提交后**同一事务**内推进（见规则 §4 回合制行），与 RTS 定时推进并存但路径分离。

**落地位置**：

- `rts_scheduler.py`、`rts_ws.py`、`api/trading_ws.py`
- `03-` §三 RTS 表、`08-` §5.1（2026-05-19 条目）

---

## 考虑过的方案

| 方案 | 优点 | 缺点 | 未采用原因 |
|------|------|------|------------|
| 客户端轮询时服务端顺便 tick | 无调度器 | 轮询风暴；GET 有副作用 | 违反 HTTP 语义 |
| 每个 `/actions` 立即 simulate 一整 tick | 响应「快」 | 与定时 tick 竞态；难 WS 对齐 | 已出现双写类 bug |
| **独立调度器 + HTTP 只读（已采纳）** | 行为可预测；易测 | 需维护后台任务 | 2026-05-19 已落地并修过多项 bug |

---

## 后果

### 正面

- 前端用 `lib/rtsWebSocket.ts` 收 tick；30s 轮询仅 fallback
- 日志与断点可集中在 scheduler

### 负面 / 代价

- 本地须保证 scheduler 在跑；否则 RTS 局「卡住」
- 初学者易在 handler 里「为了方便」调用 advance — **禁止**

### 给初学者的操作提示

- **可以做的**：改 tick 间隔、改 `maybe_advance_rts` 内逻辑；改 WS 消息格式（注意 commit 顺序）
- **不要做的**：在 `GET /state` 里 `advance_round()`；在 commit 前 `broadcast(finished)`
- **相关阅读**：`blueprint-coding.mdc` §4、`03-` 浮生记 RTS 表
