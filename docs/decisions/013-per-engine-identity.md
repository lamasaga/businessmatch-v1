# ADR-013：引擎独立视觉与交互身份

**日期**：2026-06-23  
**状态**：已采纳  
**触发**：M1（在多个可行方案中做选型）、R1（新赛制 / 新引擎的首个落地）

---

## 上下文

项目将陆续落地四个及以上商业模拟赛引擎（浮生记 FST、TechVenture、OPS 产销运营、金融投研等）。用户明确反馈：当前学生端体验像「网页上点点点的复杂 Excel」，并且要求**每个赛事引擎都是独立的「游戏」**——拥有独立的配色、UI、交互逻辑、音效与动效；除非显式说明参考某引擎，否则不能被其他引擎影响。

这一要求如果处理不好，会导致：
- 新引擎为了赶工直接复用 FST 的深色主题和组件，视觉上千篇一律。
- 共享组件库越做越大，最终变成所有引擎被同一套设计绑架。
- 学生难以通过界面一眼区分不同赛事，降低沉浸感和品牌辨识度。

因此需要把「每个引擎独立身份」上升为架构级约束。

---

## 决策

我们决定：**每个赛事引擎拥有独立的视觉与交互身份（per-engine identity）**。

具体规则：

1. **独立设计系统**：每个引擎拥有专属的 design tokens（颜色、字体、圆角、阴影）、UI 布局、音效、动效、图标风格。
2. **引擎目录隔离**：引擎专属资源放在 `frontend/public/games/<engine-id>/` 和 `frontend/src/games/<engine-id>/`，不得直接引用其他引擎目录下的视觉资源。
3. **共享层只到基础组件**：平台级共享组件（Toast、Loading、Button 等）可复用，但视觉层（主题、配色、布局、动效）默认不继承。
4. **显式引用才允许复用**：若新引擎希望参考某引擎的视觉/交互，必须在 PRD、设计文档或代码注释中显式声明「参考 XXX 引擎」；否则视为违规。
5. **PRD 中必须包含视觉与交互规范**：每个引擎的 PRD 须独立描述其配色方向、核心动效、音效清单、交互范式。
6. **默认禁用全局深色主题**：不再把「整体深色」作为平台默认；每个引擎自行决定明暗风格。

---

## 考虑过的方案

| 方案 | 优点 | 缺点 | 未采用原因 |
|------|------|------|------------|
| A. 所有引擎共用一套统一主题 | 开发快、一致性强 | 千篇一律、缺乏游戏感、无法体现不同赛事特色 | 与用户要求直接冲突 |
| B. 每个引擎完全独立，包括基础组件 | 最大程度自由 | 重复造轮子、维护成本高、平台感弱 | 过度设计，基础组件可共享 |
| C. **分层独立：共享基础组件 + 引擎独立视觉层（已采纳）** | 兼顾效率与个性、符合游戏产品规律 | 需要为每个引擎单独投入设计/前端人力 | 最符合当前阶段目标 |

---

## 后果

### 正面

- 每个引擎都能形成自己的「游戏感」和识别度。
- 避免一个引擎的设计债扩散到整个平台。
- 为后续营团、赛季、OPC 等场景的多引擎组合提供清晰的视觉边界。
- FST 可率先从深色 Excel 风格转向轻盈商旅风格，成为其他引擎的参照样板（但非默认继承）。

### 负面 / 代价

- 每新增一个引擎，都需要单独产出视觉与交互规范，增加前期设计成本。
- 共享组件库需要更抽象，避免夹带特定引擎的视觉假设。
- 前端同学需要熟悉不同引擎的设计 tokens，切换成本略高。

### 给初学者的操作提示

- **可以做的**：
  - 在 `frontend/src/games/<engine-id>/` 下定义引擎专属 CSS 变量和主题。
  - 为每个引擎配置独立的音效清单和 BGM。
  - 在 PRD 中专门写一节「视觉与交互设计规范」。
- **不要做的**：
  - 不要直接把 FST 的配色文件 import 到 TechVenture/OPS/金融引擎中。
  - 不要把某个引擎的动效组件未经评审就作为「通用组件」塞进 `components/game/`。
  - 不要在 UI 中默认继承平台的深色主题，除非该引擎 PRD 明确选择深色。
