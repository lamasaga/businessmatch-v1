# ADR-001: 文档约束层与蓝图编程

**日期**：2026-05-21  
**状态**：已采纳  
**触发**：M4（全局架构模式 — 人机协作方式）

---

## 上下文

　　本项目**主要用 AI 辅助写代码**。LLM 每次新对话从零开始，容易忘记域边界、Phase 范围、命名约定，导致返工和架构漂移。需要一种不依赖「人脑记忆」和「聊天历史」的一致性机制。

---

## 决策

　　采用**蓝图编程（Blueprint Coding）**：以根目录 **`00～09` 编号文档** + **`.cursor/rules/` 自动注入规则** 作为权威约束层；代码实现必须在文档定义的框架内产出，争议时**以文档为准**回改代码或更新文档（推送前对齐）。

**落地位置**：

- 战略/战术/会话：`CLAUDE.md`（Claude Code 入口）· `agent.md`（其他 AI 工具）· `00-PROJECT.md`～`04-ROADMAP.md`
- AI 护栏：`.cursor/rules/blueprint-coding.mdc`、`docs-align-before-push.mdc`
- 方法论手册：`蓝图编程方法论——AI辅助大型工程实践指南.md`

---

## 考虑过的方案

| 方案 | 优点 | 缺点 | 未采用原因 |
|------|------|------|------------|
| 仅靠 Code Review + 口头约定 | 轻量 | AI 新会话无法继承；新人/AI 易越界 | 无法支撑 AI 为主的工作流 |
| 把所有规则写进代码注释 | 离代码近 | 分散、难给产品/非开发读；易过时 | 不适合跨域、Phase 级约束 |
| **文档约束层 + 规则自动注入（已采纳）** | 可 @ 引用、可版本管理、可给 AI 读 | 需维护文档与代码同步 | 与项目规模、AI 协作方式匹配 |

---

## 后果

### 正面

- 新对话通过 attach `00～09` 与规则快速对齐
- 推送前有强制「文档对齐门」，减少文档与代码分裂

### 负面 / 代价

- 小改动也可能要更新 `03-ENGINEERING.md`；习惯成本对初学者略高

### 给初学者的操作提示

- **可以做的**：开会话前读 `CLAUDE.md`「项目概览」；按任务 @ `03-ENGINEERING.md`、`04-ROADMAP.md`、相关 ADR
- **不要做的**：不让 AI「凭感觉」加新路由/新表而不改 `03-ENGINEERING.md` / 域表
- **相关阅读**：`03-ENGINEERING.md` §AI_DEFAULT / 开发流程 · `docs/decisions/README.md`
