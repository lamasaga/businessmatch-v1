# ADR-003: 域边界与表归属

**日期**：2026-05-21  
**状态**：已采纳  
**触发**：M3

---

## 上下文

　　赛事平台天然有多块数据：用户账号、比赛场次、某场浮生记的价格表、TechVenture 队伍策略。若任意模块都能改任意表，AI 和人类都容易「从 trading 里直接改 `competition_events`」，破坏不变式，难以测试和拆赛制。

---

## 决策

　　按**域（Domain）**划分所有权：

| 域 | 拥有赛事「元数据」与办赛流程 | 拥有对局「运行时」数据 | 拥有配置/内容 |
|----|------------------------------|------------------------|---------------|
| **arena** | `competition_events`、`competition_participants`、`organizer_profiles`、`arena_teams`… | — | — |
| **cybercore** | — | — | `game-configs/*.yaml`、世界内容包 |
| **games/trading** | — | `trading_rounds`、`trading_decisions`、`trading_prices`… | — |
| **games/techventure** | — | `tv_*` 表 | — |
| **career** | — | `xp_events`（账本） | — |
| **identity** | `users` | — | — |

　　跨域须通过**服务函数或 API**，禁止在他域代码里直接 `session` 写入他域表。`models/trading_competition.py` **仅 re-export**，禁止写新业务。

**落地位置**：

- `webapp/backend/app/domains/arena/`
- `webapp/backend/app/games/trading/`、`games/techventure/`
- `webapp/backend/app/domains/career/`
- 详表：`.cursor/rules/blueprint-coding.mdc` §1、`domains/arena/ARCHITECTURE.md`、`02-ARCHITECTURE.md` §高层架构、`03-ENGINEERING.md` §一 后端 API 全表

---

## 考虑过的方案

| 方案 | 优点 | 缺点 | 未采用原因 |
|------|------|------|------------|
| 所有表放 `models/` 一个大包 | 找模型快 | 无边界；赛制越多越乱 | 无法约束 AI |
| 按前端（学生/组织者）分包 | 贴合 UI | 同一对局被两端改，逻辑重复 | 后端不应镜像前端 |
| **按业务能力域 + games 运行时（已采纳）** | 与产品语言一致；易扩展赛制 | 要学习域表 | 已落地 Arena/Career 分包 |

---

## 后果

### 正面

- 新增 TechVenture 时运行时表集中在 `games/techventure`，不污染 arena 通用模型
- Code Review / AI 自检有明确「禁止事项」列

### 负面 / 代价

- 跨域功能（赛后发 XP）要多跳一层调用链

### 给初学者的操作提示

- **可以做的**：在 `games/trading` 里读 arena 提供的 `event_id`；通过 arena 服务创建场次
- **不要做的**：在 `engine.py` 里 `db.query(CompetitionEvent)` 并改状态字段（应调 arena 层函数）
- **相关阅读**：ADR-007（career 入账）、`02-ARCHITECTURE.md` §域表、`03-ENGINEERING.md` §一 后端 API 全表
