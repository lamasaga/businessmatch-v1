# PRD 写作指南 · 商识唯智

> **适用对象**：AI 辅助写作、产品经理、引擎设计师
> **适用范围**：商识唯智 游戏引擎 PRD、功能模块 PRD、系统级 PRD
> **版本**：v1.0
> **最后更新**：2026-06-09

---

## 一、为什么需要这份指南

PRD（Product Requirements Document，产品需求文档）是产品从"想法"到"代码"的唯一桥梁。一份好的 PRD 能让设计师画出正确的图、让开发写出正确的代码、让测试测到正确的点，让各方对"我们要做什么"有**零歧义**的共识。

**这份指南的目标是：**

1. **标准化**：让商识唯智的所有 PRD 拥有一致的结构、术语和深度
2. **可执行**：把 PRD 写作变成可流程化的步骤，AI 和人类都能按图索骥
3. **可审视**：提供明确的检查清单，写完能自审，评审能对标
4. **可追踪**：PRD 中的每一个需求都能在代码和测试中找到对应

## 二、大厂 PRD 核心标准（行业共识）

### 2.1 字节跳动标准

| 维度 | 要求 |
|------|------|
| **一句话描述** | 任何产品/功能必须能用一句话讲清"是什么、给谁用、解决什么问题" |
| **用户故事** | 每个功能必须从用户视角写故事：`作为<角色>，我希望<动作>，以便<价值>` |
| **流程图必配** | 涉及多步骤交互必须附流程图（非可选） |
| **数据埋点** | 功能上线必须有可量化的成功指标和埋点方案 |
| **边界清晰** | 明确写出"做什么"和"不做什么" |

### 2.2 阿里巴巴标准

| 维度 | 要求 |
|------|------|
| **业务背景** | 先讲清楚"为什么要做"，再讲"做什么" |
| **目标可量化** | 业务目标必须是 SMART 原则（具体、可衡量、可达成、相关、有时限） |
| **范围界定** | 明确本期/下期/不做，防止范围蔓延 |
| **功能详述** | 每个功能模块包含：输入、处理逻辑、输出、异常分支 |
| **验收标准** | 每条需求必须有可验证的验收条件（Given-When-Then 格式） |

### 2.3 腾讯标准

| 维度 | 要求 |
|------|------|
| **需求背景** | 包含用户痛点、市场机会、竞品对标 |
| **用户场景** | 描述具体的使用场景（时间、地点、人物、事件） |
| **功能架构** | 用架构图展示模块关系，避免功能孤岛 |
| **交互说明** | 关键页面必须有交互原型或详细的状态流转 |
| **数据指标** | 定义核心指标（留存、转化、活跃）和观测方式 |

### 2.4 美团标准

| 维度 | 要求 |
|------|------|
| **业务目标** | 与 OKR 对齐，明确业务价值 |
| **需求范围** | 功能清单 + 优先级（P0/P1/P2） |
| **功能逻辑** | 用伪代码或决策表描述复杂计算逻辑 |
| **异常处理** | 必须覆盖所有异常路径（网络失败、权限不足、数据为空等） |
| **数据口径** | 指标定义必须精确到计算公式和取值范围 |

### 2.5 大厂共识：优秀 PRD 的 7 个特征

1. **读者友好**：技术、设计、运营、测试都能读懂自己关心的部分
2. **无歧义**：同一个词在全文中含义一致，缩写首次出现必须展开
3. **可验证**：每条需求都有明确的"怎么算做完了"
4. **可回溯**：每个决策都有"为什么这么做"的解释
5. **完整闭环**：从用户进入 → 核心操作 → 结果反馈 → 异常处理，不留缺口
6. **数据驱动**：有指标、有埋点、有评估方式
7. **向前兼容**：考虑扩展性，不锁死未来可能性

## 三、商识唯智 PRD 标准结构（10 章模板）

商识唯智的 PRD 采用**10 章结构**，每一章有明确的写作目标和必须包含的内容。以下按章节详细说明。

### Chapter 0：文档头（Document Header）

**目的**：让读者在 10 秒内了解这份 PRD 是什么、属于谁、什么状态。

**必须包含**：

```markdown
# [引擎/模块名] PRD · [中文名]

> **引擎简称**：[简称]
> **引擎 ID**：`[唯一标识]`
> **配置 ID**：`[配置包标识]`
> **版本**：[语义化版本，如 1.0.0]
> **运行时**：`phaser` | `react-game`
> **设计模式**：`standalone` | `world-integrated`
> **最后更新**：[YYYY-MM-DD]
> **状态**：🟡 草案 / 🟢 已定稿 / 🔴 已冻结
```

**写作检查点**：
- [ ] 引擎 ID 是否与 `03-ENGINEERING.md` 中定义的一致？
- [ ] 配置 ID 是否与 `content/game-configs/` 中的文件名对应？
- [ ] 版本是否遵循语义化版本（MAJOR.MINOR.PATCH）？
- [ ] 运行时选型是否按 `02-ARCHITECTURE.md` §1.2 执行？

**必须包含的字段**：

| 字段 | 说明 | 示例 |

| 世界区域 | 关联的世界区域（如有） | `yangtze_6` |

| 前端路由 | 前端页面路径 | `/games/:id/play` |

**写作检查点**：
- [ ] 所有标识符在项目中全局唯一？
- [ ] 表前缀是否与已有引擎不冲突？（查 `03-ENGINEERING.md` §数据表索引）
- [ ] 路由是否与 `main.py` 中已挂载路由不冲突？

### Chapter 2：产品定位（Product Positioning）

**目的**：回答"这是什么""给谁玩""玩多久""能学到什么"。

**必须包含的 4 个子章节**：

#### 2.1 一句话玩法

用一句话概括核心玩法，格式模板：

> **[时间/节奏特征] 的 [游戏类型]——[核心操作]，以 [胜利条件] 排名决胜负。**

示例（FST）：
> 5 秒一 tick 的即时长三角六城物流商战：玩家在相邻城市间低买高卖、投资运力，以比赛结束时的**总资产**排名决胜负。

**写作要求**：
- 不超过 80 字
- 必须包含：节奏、类型、核心操作、胜利条件
- 避免使用内部术语（如"tick"对非技术读者需解释）

#### 2.2 教育目标

用表格列出本引擎要培养的**具体能力**，每条能力包含：

| # | 能力 | 说明（在游戏中如何体现） |
|---|------|------------------------|

**写作要求**：
- 3~8 条，不宜过多
- 每条必须能在游戏机制中找到对应（即"可教性"验证）
- 使用动名词短语（如"战略路线选择与取舍"）

#### 2.3 目标受众

| 维度 | 说明 |
|------|------|
| 目标年龄 | 如 14~22 岁 |
| 适合学段 | 如初中高年级至大学低年级 |
| 单局时长 | 如 8~20 分钟 |
| 单场人数 | 如练习赛 1+3 AI，正式赛 4~40 人 |
| 决策类型 | 如实时操作 + 资源管理 + 空间套利 |

#### 2.4 单局节奏

用时间线或表格描述一局游戏的完整时间线：

```
┌─────────────────────────────────────┐
│  0:00  阶段一（时长）— 做什么        │
│  x:xx  阶段二（时长）— 做什么        │
│  ...                                │
└─────────────────────────────────────┘
```

**写作检查点**：
- [ ] 一句话玩法是否能让完全不了解项目的人在 10 秒理解？
- [ ] 教育目标是否都能在游戏机制中找到对应？
- [ ] 目标受众是否与教育目标匹配？
- [ ] 单局时长是否符合目标受众的注意力特征？

### Chapter 3：核心循环（Core Loop）

**目的**：描述游戏从创建到结束的完整生命周期，以及关键状态流转。

**必须包含的 3 个子章节**：

#### 3.1 流程图

用 ASCII 流程图或文字流程图描述完整生命周期：

```
创建 match
  ├── 读取配置
  ├── 创建 ArenaMatch
  └── 创建参与者
      ↓
  玩家加入
      ↓
  开赛
      ├── 初始化运行时
      └── 启动调度器
      ↓
  决策/推进循环
      ├── 玩家决策
      ├── 推进/结算
      └── 状态广播
      ↓
  结束判定
      ├── 排名
      ├── 奖励发放
      └── 状态变更
```

**写作要求**：
- 每个节点代表一个**业务动作**（不是技术函数）
- 分支条件必须标注清楚
- 循环部分用 ↓ 箭头明确标示

#### 3.2 关键状态机

用表格描述 match 级别的状态流转：

| 状态 | 触发条件 | 可执行操作 |
|------|----------|-----------|
| `draft` | 刚创建 | 组织者配置、邀请玩家 |
| `registration` | 开放加入 | 玩家输入房间码加入 |
| `playing` | 开赛 | 提交 action、查看 state |
| `finished` | 比赛结束 | 查看结果、复盘 |

如果是回合制，还需描述**轮次状态机**（`pending` → `open` → `settled`）。

#### 3.3 推进规则

描述游戏如何"向前走"：

- **RTS 模式**：tick 间隔、推进者（谁负责推进）、并发安全、HTTP 只读原则、广播顺序
- **回合制模式**：谁决定开轮、谁触发结算、练习赛自动推进逻辑

**写作检查点**：
- [ ] 流程图是否覆盖了从创建到结束的完整路径？
- [ ] 状态机是否覆盖所有可能的状态，无遗漏？
- [ ] 推进规则是否与 `03-ENGINEERING.md` §RTS 单写者原则一致？
- [ ] 异常路径（如玩家中途退出）是否在流程中标注？

### Chapter 4：决策设计（Decision Design）

**目的**：精确描述玩家"能做什么""怎么做""有什么限制"。这是 PRD 中最关键的章节之一。

**必须包含的 4 个子章节**：

#### 4.1 玩家可操作列表

用表格列出所有玩家可执行的操作/决策：

| Action | 英文名 | Payload Schema | 说明 |
|--------|--------|----------------|------|
| 买入 | `buy` | `{"product_id": string, "quantity": int}` | 按城市 ask 价格买入商品 |

**写作要求**：
- 每个操作必须有**英文名**（用于代码中的枚举/常量）
- 每个操作必须有**JSON Schema** 描述输入
- 如果是回合制策略游戏，用"决策项"替代"Action"

#### 4.2 校验规则

对每个操作，列出**所有校验条件**：

```markdown
#### `buy` 校验

1. `quantity >= 1`
2. `product_id` 存在于配置中
3. 玩家当前不在运输途中
4. 当前城市该商品 `ask > 0`
5. `ask * quantity <= cash`
6. 买入后库存体积 `+ quantity * volume <= storage_capacity`
```

**写作要求**：
- 按编号列出，方便开发和测试逐条对照
- 校验失败必须返回明确的错误信息（建议写明）
- 校验顺序有意义时，按执行顺序排列

#### 4.3 执行效果

用表格描述每个操作执行后的**状态变更**：

| Action | 执行效果 |
|--------|----------|
| `buy` | `cash -= ask * qty`；`inventory[pid] += qty`；城市池 `-qty` |

#### 4.4 特殊规则

列出不在上述标准操作中的特殊机制：

- 运输途中无法交易
- 每 tick 收购上限
- 相邻限制
- 车辆上限

**写作检查点**：
- [ ] 每个操作是否有明确的英文名？
- [ ] 校验规则是否覆盖了所有边界条件（如负数、零值、越界）？
- [ ] 执行效果是否精确到状态变更公式？
- [ ] 特殊规则是否会被遗漏在开发中？

### Chapter 5：结算规则（Settlement Rules）

**目的**：描述游戏"怎么算分""怎么排名"，是引擎的核心算法契约。

**必须包含的 4 个子章节**：

#### 5.1 结算函数签名

写出 Python 函数签名（或伪代码）：

```python
def settle_round(ctx: SettlementContext, config_id: str) -> dict[str, Any]:
    """结算主函数。纯函数、幂等、不读写数据库。"""
```

如果是 RTS 模式，还需写出 tick 推进函数：

```python
def advance_one_tick(db: Session, event: ArenaMatch) -> None:
    """推进一个 tick。包含市场演化、action 执行、定价、资产刷新。"""
```

**写作要求**：
- 必须标注函数是否为**纯函数**（无副作用）
- 必须标注是否**幂等**
- 参数和返回值类型必须明确

#### 5.2 结算流程

用编号步骤描述结算的**精确顺序**：

```markdown
#### Tick 推进的 8 步顺序

1. tick 计数器 +1，更新 phase
2. 推进在途玩家
3. 执行真人 pending actions
4. 自然市场池更新
5. 重新定价
6. AI 决策（仅练习赛）
7. 执行 AI actions + 再次定价
8. 刷新所有玩家总资产
9. 持久化新 Round
10. 结束判定
```

**写作要求**：
- 步骤顺序**不可调换**时，必须说明原因
- 每个步骤引用对应的代码文件（如"见 `rts_pricing.py`"）
- 条件分支必须标注清楚

#### 5.3 核心公式

用代码块写出所有关键计算公式：

```
surplus = production - consumption
factor = 1.0 - 0.04 * (surplus / max(consumption, 1))
mid = base_price * factor
mid = clamp(mid, price_range.low, price_range.high)
```

**写作要求**：
- 公式中的每个变量必须在上下文中有定义
- 使用标准数学符号（`√` 写为 `sqrt()`，`Σ` 写为 `sum()`）
- 边界条件（clamp、min、max）必须写出

#### 5.4 最终排名

描述比赛结束时如何计算排名：

```
total_assets = cash + sum(inventory[pid] * current_city_bid[pid])
按 total_assets 降序排名
```

**写作检查点**：
- [ ] 结算函数是否符合"纯函数、幂等、不读写数据库"的引擎规范？
- [ ] 结算步骤顺序是否与实际代码一致？
- [ ] 公式中的每个变量是否都有取值范围和单位？
- [ ] 排名规则是否有平局处理机制？

### Chapter 8：前端局内（Frontend In-Game）

**目的**：描述玩家看到什么、怎么交互。

**必须包含的 5 个子章节**：

#### 8.1 运行时选型

说明选择 `phaser` 或 `react-game` 的理由：

> 选择 **`phaser`** 运行时，因为玩法核心包含地图上的城市节点和商队移动动画。

#### 8.2 组件清单

## 四、PRD 写作流程（AI 可执行的 7 步法）

以下是 AI 辅助写作 PRD 的标准流程。每一步有明确的输入、输出和验收标准。

### Step 1：需求对齐（Alignment）

**输入**：
- 引擎/功能的需求说明（来自产品经理或设计师）
- `04-ROADMAP.md` 中的 Phase 门控
- `03-ENGINEERING.md` 中的技术约束

**输出**：
- 一句话玩法（Chapter 2.1）
- 教育目标列表（Chapter 2.2）
- 目标受众画像（Chapter 2.3）
- 单局节奏草图（Chapter 2.4）

**验收标准**：
- [ ] 一句话玩法能让完全不了解的人理解
- [ ] 教育目标与需求说明一致
- [ ] 单局时长符合目标受众注意力特征

---

### Step 2：机制设计（Mechanism Design）

**输入**：
- Step 1 的输出
- 竞品分析或参考赛事描述
- 已有的类似引擎 PRD（如 FST、TECH）

**输出**：
- 核心循环流程图（Chapter 3.1）
- 状态机定义（Chapter 3.2）
- 玩家操作列表（Chapter 4.1）
- 校验规则（Chapter 4.2）
- 执行效果（Chapter 4.3）
- 特殊规则（Chapter 4.4）

**验收标准**：
- [ ] 流程图覆盖完整生命周期
- [ ] 每个操作有明确的输入、校验、效果
- [ ] 校验规则覆盖所有边界条件
- [ ] 机制设计不与已有引擎重复或冲突

---

### Step 3：结算设计（Settlement Design）

**输入**：
- Step 2 的机制设计
- 引擎规范（`docs/ENGINE.md`）

**输出**：
- 结算函数签名（Chapter 5.1）
- 结算步骤（Chapter 5.2）
- 核心公式（Chapter 5.3）
- 排名规则（Chapter 5.4）

**验收标准**：
- [ ] 结算函数为纯函数、幂等
- [ ] 所有公式中的变量有定义和取值范围
- [ ] 步骤顺序合理且有说明
- [ ] 公式可转化为代码实现

---

### Step 4：数据与 API 设计（Data & API Design）

**输入**：
- Step 2 和 Step 3 的输出
- `03-ENGINEERING.md` 中的 API 规范
- 已有引擎的数据模型（如 `models.py`）

**输出**：
- 数据库表设计（Chapter 7.1）
- 运行时状态结构（Chapter 7.2）
- API 端点列表（Chapter 7.3）
- WebSocket 消息类型（Chapter 7.4，如有）

**验收标准**：
- [ ] 表名使用正确的前缀
- [ ] API 路径与 `main.py` 路由不冲突
- [ ] 状态结构 JSON 是合法的
- [ ] 大规模扩展瓶颈有缓解方案

---

### Step 5：前端设计（Frontend Design）

**输入**：
- Step 2 的机制设计
- `02-ARCHITECTURE.md` 中的运行时选型指南
- 已有的前端组件库（`docs/UI-LIBRARY.md`）

**输出**：
- 运行时选型说明（Chapter 8.1）
- 组件清单（Chapter 8.2）
- 交互流程（Chapter 8.3）
- 状态管理接口（Chapter 8.4）
- 素材需求（Chapter 8.5）

**验收标准**：
- [ ] 运行时选型有合理理由
- [ ] 组件路径符合项目目录规范
- [ ] 交互流程覆盖所有玩家操作
- [ ] 状态管理与已有 store 风格一致

---

### Step 6：配置设计（Configuration Design）

**输入**：
- Step 2~5 的所有输出
- 已有引擎的 YAML 配置（如 `fstrading.yaml`）

**输出**：
- YAML 顶层结构（Chapter 9.1）
- 所有参数说明（Chapter 9.2）

**验收标准**：
- [ ] YAML 结构与已有配置风格一致
- [ ] 所有硬编码数值都有对应的配置参数
- [ ] 参数命名使用 snake_case
- [ ] 默认值合理且经过计算/估算

---

**验收标准**：
- [ ] 通过第五章的所有审视角度

## 五、PRD 审视清单（Review Checklist）

写完 PRD 后，从以下 8 个角度审视。每个角度有具体的检查项。

### 5.1 完整性审视（Completeness）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 是否包含全部 10 个章节？ | 每个章节都有内容，无空缺 |
| 2 | 流程图是否覆盖完整生命周期？ | 从创建到结束，无断点 |
| 3 | 状态机是否覆盖所有状态？ | 无遗漏的状态值 |
| 4 | 是否包含异常处理？ | 每个操作都有失败/异常路径 |
| 5 | 是否包含性能指标？ | 至少定义 3 个性能红线 |

### 5.2 一致性审视（Consistency）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 术语是否全文一致？ | 同一个概念只有一个名称 |
| 2 | 标识符是否全局唯一？ | 引擎 ID、配置 ID、表前缀不与已有冲突 |
| 3 | 公式符号是否统一？ | 同一符号在全文中含义一致 |
| 4 | 章节间是否无矛盾？ | Chapter 4 的操作与 Chapter 5 的结算能对应 |
| 5 | 与现有文档是否一致？ | 与 `03-ENGINEERING.md`、`02-ARCHITECTURE.md` 无矛盾 |

### 5.3 可执行性审视（Executability）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 每个需求是否可验证？ | 有明确的验收条件 |
| 2 | 公式是否可转化为代码？ | 每个公式都能写成函数 |
| 3 | 校验规则是否可测试？ | 每条规则都能写单元测试 |
| 4 | API 是否可对接？ | 路径、方法、参数都明确 |
| 5 | Checklist 是否可逐项勾选？ | 每个条目有明确的完成标准 |

### 5.4 可理解性审视（Comprehensibility）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 一句话玩法是否易懂？ | 非项目人员 10 秒理解 |
| 2 | 是否有过多内部术语？ | 首次出现的缩写都有展开 |
| 3 | 流程图是否自解释？ | 不读文字也能理解大致流程 |
| 4 | 表格是否比段落更清晰？ | 结构化信息优先用表格 |
| 5 | 代码块是否有注释？ | 复杂公式有关键步骤说明 |

### 5.5 可扩展性审视（Extensibility）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 参数是否配置化？ | 无硬编码数值 |
| 2 | AI 档位是否预留扩展？ | 未实现的档位有占位说明 |
| 3 | 事件/特殊机制是否可插拔？ | 新事件类型能不改动核心逻辑加入 |
| 4 | 大规模扩展是否有方案？ | 40 人局的瓶颈和缓解方案 |
| 5 | 是否预留未来 Phase 的钩子？ | 与 `04-ROADMAP.md` 的后续 Phase 兼容 |

### 5.6 教育性审视（Educational Value）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 教育目标是否可衡量？ | 每条目标有对应的游戏机制 |
| 2 | 玩法是否传递目标能力？ | 玩家"不得不"使用目标能力才能赢 |
| 3 | 难度曲线是否合理？ | 从简单到复杂，有学习空间 |
| 4 | 反馈是否即时？ | 玩家操作后能快速看到结果 |
| 5 | 是否有反思空间？ | 结算/复盘能让玩家理解为什么赢/输 |

### 5.7 技术可行性审视（Technical Feasibility）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 结算是否能在性能红线内完成？ | 40 人局 < 200ms |
| 2 | 数据库设计是否符合规范？ | 表前缀正确，字段类型合理 |
| 3 | API 设计是否符合 REST 规范？ | 方法、路径、状态码合理 |

### 5.8 风险审视（Risk Assessment）

| # | 检查项 | 通过标准 |

## 七、常见错误与避坑指南

### 7.1 结构层面

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 缺少 Chapter 1 元信息 | 开发找不到表前缀和路由 | 所有标识符在文档头部集中声明 |
| 流程图与状态机不一致 | 开发和测试理解分歧 | 流程图中的状态值与状态机表格完全一致 |
| 缺少异常处理 | 线上出现未预期的错误 | 每个操作至少写 3 条异常路径 |
| 缺少性能指标 | 上线后性能不达标 | 至少定义 3 个可测量的性能红线 |

### 7.2 内容层面

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 教育目标与机制脱节 | 玩家学不到东西 | 每条教育目标都能在机制中找到对应 |
| 公式缺少变量定义 | 开发理解错误 | 公式首次出现时定义每个变量 |
| 校验规则不完整 | 线上出现非法数据 | 覆盖空值、越界、负数、权限、状态冲突 |
| 默认值拍脑袋 | 平衡性崩溃 | 默认值有估算过程或参考来源 |

### 7.3 协作层面

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| PRD 与代码不同步 | 文档失去参考价值 | 每次代码变更同步更新 PRD |
| 多个 PRD 术语不一致 | 跨引擎开发混乱 | 使用 `00-TERMINOLOGY.md` 中的统一术语 |
| 新引擎不参考已有 PRD | 重复造轮子 | 新引擎 PRD 开头列出可复用的模式 |
| Phase 门控被忽视 | 做了不该做的功能 | 每写一章对照 `04-ROADMAP.md` |
