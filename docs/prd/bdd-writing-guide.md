## 一、什么是 BDD 以及为什么需要它

### 1.1 BDD 定义

**BDD（Behavior-Driven Development，行为驱动开发）** 是一种敏捷软件开发方法，核心思想是：

> **用业务人员、开发人员、测试人员都能理解的自然语言，精确描述软件的行为。**

BDD 由 Dan North 于 2006 年提出，它把 TDD（测试驱动开发）中的"测试"视角转换为"行为"视角，让需求描述从"验证代码是否正确"变成"验证系统是否按预期行为工作"。

### 1.2 BDD 的三重价值

| 价值 | 说明 |
|------|------|
| **统一语言** | 业务、开发、测试用同一套语言描述需求，消除"我以为"和"实际上"的鸿沟 |
| **活文档** | BDD 文档随代码同步更新，永远不会过期的需求文档 |
| **验收标准** | 每个 Scenario 都是可自动化的验收测试，开发完成 = 测试通过 |

### 1.3 BDD 在商识唯智的定位

在商识唯智 中，BDD 文档承担以下角色：

1. **PRD 的验证层**：PRD 描述"做什么"，BDD 描述"怎么做才对"（精确到输入输出）
2. **开发的脚手架**：开发人员在写代码前，先看 BDD 知道自己要实现什么行为
3. **QA 的测试用例**：QA 可以直接将 BDD 场景转化为自动化测试脚本
4. **Code Review 的标尺**：Reviewer 对照 BDD 检查代码是否覆盖所有场景

**BDD 与 PRD 的关系**：

```
PRD（产品需求文档）
    ↓ 细化、量化、可验证化
BDD（行为场景文档）
    ↓ 自动化
自动化测试（Cypress / Pytest / 单元测试）
```

## 二、大厂 BDD 核心标准（行业共识）

### 2.1 Dan North 原始原则（BDD 之父）

| 原则 | 说明 |
|------|------|
| **Given = 上下文** | 描述场景发生前的系统状态，不是动作 |
| **When = 事件** | 描述触发行为的单一事件 |
| **Then = 结果** | 描述可观测的预期结果，必须是可验证的 |
| **一个场景 = 一个行为** | 不要在一个 Scenario 里测试多个独立行为 |
| **业务语言** | 不用技术术语（如"调用 API""写数据库"），用业务术语（如"提交决策""获得金币"） |

### 2.2 Cucumber 官方规范

| 规范 | 要求 |
|------|------|
| **Feature 必须有业务价值** | 每个 Feature 开头用 `As a / I want / So that` 说明价值 |
| **Scenario 必须可独立执行** | 不依赖其他 Scenario 的执行结果 |
| **具体的数据** | 用具体数值（"小林获得金币 30"）而非抽象描述（"小林获得金币"） |
| **无 UI 实现细节** | 不写"点击按钮"，写"提交决策"；UI 变更不影响场景 |
| **无技术实现细节** | 不写"发送 POST 请求"，写"比赛结束并结算" |

### 2.3 Google Testing 标准

| 标准 | 要求 |
|------|------|
| **Test as Documentation** | 测试代码就是文档，读起来像说明书 |
| **One Concept Per Test** | 每个测试只验证一个概念 |
| **DAMP not DRY** | 测试代码优先可读性（Descriptive And Meaningful Phrases），不要过度抽象 |
| **AAA Pattern** | Arrange（准备）→ Act（执行）→ Assert（断言），对应 Given-When-Then |

### 2.4 Amazon Working Backwards（逆向工作法）

Amazon 的 PR/FAQ 流程与 BDD 高度契合：

| 环节 | BDD 对应 |
|------|----------|
| **Press Release** | Feature 标题 + 用户故事（As a / I want / So that） |
| **FAQ** | Scenario 中回答"如果...会怎样"的边界场景 |
| **Working Backwards** | 从"用户看到什么结果"倒推 Given 条件 |

### 2.5 大厂共识：优秀 BDD 的 7 个特征

1. **业务可读**：非技术人员能读懂并判断"这是否是我想要的"
2. **精确具体**：用具体数值、具体状态，不用"某些""可能"
3. **可自动化**：每个 Then 都能转化为断言语句
4. **独立运行**：Scenario 之间不共享状态，可以乱序执行
5. **单一职责**：一个 Scenario 只测一个行为分支
6. **边界完整**：覆盖正常路径、异常路径、边界条件
7. **数据闭环**：Given 准备的数据在 Then 中有明确的验证点

## 三、Gherkin 语法规范

### 3.1 关键字速查表

| 关键字 | 用途 | 使用规则 |
|--------|------|----------|
| `Feature` | 功能模块 | 每个 `.feature` 文件一个，必须包含用户故事 |
| `Background` | 公共前置条件 | 可选，同一 Feature 下所有 Scenario 共享的 Given |
| `Scenario` | 具体场景 | 每个 Feature 可包含多个，描述一个完整的行为路径 |
| `Scenario Outline` | 参数化场景 | 用 `Examples` 提供多组数据，减少重复 |
| `Given` | 前置条件 | 描述系统当前状态，可以多个 |
| `When` | 触发事件 | 只描述一个动作或事件 |
| `Then` | 预期结果 | 描述可观测的结果，必须可验证 |
| `And` / `But` | 连接词 | 连接同类型的步骤（Given-And-Given, Then-But-Then） |
| `Examples` | 参数表 | 与 `Scenario Outline` 配合使用 |
| `*` | 通配步骤 | 当步骤类型不重要时使用（不推荐） |

### 3.2 语法结构模板

```gherkin
Feature: [功能名称]

  作为 [角色]
  我希望 [动作]
  从而 [价值]

  Background:
    Given [所有 Scenario 共享的前置状态]
    And [共享前置状态补充]

  Scenario: [场景标题——描述期望的结果]
    Given [具体的前置条件]
    And [前置条件补充]
    When [触发的事件]
    Then [可验证的预期结果]
    And [结果补充]

  Scenario Outline: [参数化场景标题]
    Given [前置条件]
    When [触发事件] <parameter>
    Then [预期结果] <expected>

    Examples:
      | parameter | expected |
      | value_1   | result_1 |
      | value_2   | result_2 |
```

### 3.3 关键字使用规则

#### Given 的规则

- **描述状态，不是动作**：❌ `Given 用户点击登录按钮` → ✅ `Given 用户已登录`
- **用完成时态**：`Given 学生已开启生涯模式`
- **可以多个，用 And 连接**：但不宜超过 5 个，过多说明场景过于复杂
- **包含具体数据**：`Given 小林的等级为 2` 而非 `Given 小林有等级`

#### When 的规则

- **只有一个 When**：一个 Scenario 只描述一个触发事件
- **用一般现在时**：`When 比赛结束并结算`
- **描述业务动作**：❌ `When 发送 POST /api/v1/trading/actions` → ✅ `When 玩家提交买入决策`
- **如果必须涉及UI，用业务术语**：`When 玩家点击「提交本轮决策」`

#### Then 的规则

- **必须是可验证的**：每个 Then 都能写出对应的断言语句
- **描述结果状态**：`Then 页面显示等级 "Lv.2"`
- **不要写实现方式**：❌ `Then 数据库中插入一条记录` → ✅ `Then 小林获得金币 30`
- **可以多个，用 And/But 连接**：验证多个维度的结果

#### And / But 的规则

- **And**：同类型步骤的延续
- **But**：反向验证或例外情况
- 示例：
  ```gherkin
  Then 小林获得金币 30
  And 小林获得钻石 2
  But 小林不获得 XP
  ```

## 四、商识唯智 BDD 标准结构

### 4.1 文档头（Document Header）

每个 BDD 文档开头必须包含：

```markdown
# [功能名] · [Phase/模块] BDD 文档

> **文档定位**：基于 `docs/prd-[xxx].md` 生成的行为驱动开发场景
> **语法**：Gherkin（Given-When-Then）
> **语言**：中文业务语言，避免技术实现细节
> **最后更新**：[YYYY-MM-DD]
```

### 4.2 Feature 组织原则

**Feature 的拆分粒度**：

- 一个 Feature 对应 PRD 中的一个**独立功能模块**
- 一个 Feature 包含 2~8 个 Scenario 为宜
- Feature 过多时拆分为多个文档

**Feature 命名**：

```markdown
## Feature N：[动词 + 名词短语]
```

示例：
- ✅ `Feature 1：生涯模式开启`
- ✅ `Feature 3：比赛结算资源入账`
- ❌ `Feature：关于生涯模式的东西`
- ❌ `Feature：career start`

### 4.3 用户故事（User Story）

每个 Feature 必须包含用户故事：

```markdown
**作为** [角色]
**我希望** [动作]
**从而** [价值]
```

**写作要求**：
- 角色必须是具体的用户类型（学生、组织者、平台设计者）
- 动作是业务行为，不是技术操作
- 价值是用户获得的收益，不是系统做的事情

### 4.4 Scenario 命名与编号

**编号规则**：

```markdown
### Scenario [Feature编号].[Scenario序号]：[场景描述]
```

示例：
- `Scenario 1.1：首次开启生涯模式`
- `Scenario 3.4：同一比赛结算幂等，不重复发放`

**命名要求**：
- 用**祈使句或陈述句**描述期望的结果
- 标题应该让读者不看正文就知道在测什么
- 包含关键条件（如"幂等""空状态""失败时"）

### 4.5 Scenario 分类体系

每个 Feature 的 Scenario 应该覆盖以下类型：

| 类型 | 说明 | 必须？ |
|------|------|--------|
| **Happy Path** | 正常流程，最理想的情况 | ✅ 必须 |
| **边界条件** | 最小值、最大值、空值、刚好满足阈值 | ✅ 必须 |
| **异常路径** | 错误输入、失败场景、降级处理 | ✅ 必须 |
| **幂等性** | 重复操作的结果一致性 | ⚠️ 涉及写入时必须 |
| **并发/竞态** | 多用户同时操作的场景 | ⚠️ 涉及并发时必须 |
| **权限控制** | 不同角色的可见性和可操作性 | ⚠️ 涉及权限时必须 |
| **数据一致性** | 多处展示同一数据的一致性 | ⚠️ 涉及多处展示时必须 |

## 五、BDD 写作流程（AI 可执行的 6 步法）

### Step 1：PRD 解构（PRD Decomposition）

**输入**：
- 已完成的 PRD 文档
- `00-TERMINOLOGY.md`（统一术语表）

**输出**：
- 功能模块清单（每个模块对应一个 Feature）
- 每个模块的关键行为点

**操作方法**：
1. 通读 PRD，按 Chapter 划分功能模块
2. 每个模块提取：角色、动作、预期结果
3. 标记需要 BDD 覆盖的模块（不是所有 PRD 内容都需要 BDD）

**哪些需要 BDD，哪些不需要**：

| 需要 BDD | 不需要 BDD |
|----------|-----------|
| 用户交互流程 | 纯技术架构设计 |
| 业务规则校验 | 代码文件路径说明 |
| 数据计算逻辑 | 性能指标定义 |
| 状态流转 | 素材需求清单 |
| 权限控制 | 部署配置 |

### Step 2：Feature 定义（Feature Definition）

**输入**：
- Step 1 的功能模块清单

**输出**：
- 每个 Feature 的用户故事（As a / I want / So that）
- Feature 之间的依赖关系

**操作方法**：
1. 为每个模块写用户故事
2. 检查用户故事是否符合 INVEST 原则：
   - **I**ndependent（独立）：Feature 之间无强依赖
   - **N**egotiable（可协商）：故事内容可讨论调整
   - **V**aluable（有价值）：对用户有明确价值
   - **E**stimable（可估算）：开发能估算工作量
   - **S**mall（小）：一个 Feature 1~3 天能完成
   - **T**estable（可测试）：能写出验收条件

### Step 3：Scenario 设计（Scenario Design）

**输入**：
- Step 2 的 Feature 定义
- PRD 中的操作列表、校验规则、边界条件

**输出**：
- 每个 Feature 的 Scenario 列表
- 标注每个 Scenario 的类型（Happy Path / 边界 / 异常 / 幂等）

**设计方法——"五问法"**：

对每个操作或规则，问五个问题：

1. **正常情况**：一切条件满足时，会发生什么？
2. **最小值**：输入刚好是最小允许值时，会发生什么？
3. **最大值**：输入刚好是最大允许值时，会发生什么？
4. **空值/缺失**：输入为空或缺失时，会发生什么？
5. **重复**：同一操作重复执行时，会发生什么？

**示例**：

PRD 规则：`买入 quantity >= 1`

| 问题 | Scenario |
|------|----------|
| 正常情况 | `Scenario：玩家买入 10 单位商品` |
| 最小值 | `Scenario：玩家买入 1 单位商品` |
| 最大值 | `Scenario：玩家买入库存上限数量的商品` |
| 空值/缺失 | `Scenario：玩家提交 quantity 为 0 的买入请求` |
| 重复 | `Scenario：玩家在同一 tick 重复提交买入` |

### Step 4：步骤撰写（Step Writing）

**输入**：
- Step 3 的 Scenario 设计

**输出**：
- 完整的 Gherkin 步骤（Given-When-Then）

**写作检查清单**：

- [ ] 每个 Given 用**完成时态**描述状态
- [ ] 每个 When 只有**一个动作**
- [ ] 每个 Then 是**可验证的断言**
- [ ] 使用**具体数据**（姓名、数值、状态值）
- [ ] 使用**业务语言**，避免技术术语
- [ ] 步骤之间用** And / But** 连接，保持层级清晰

**数据命名规范**：

| 类型 | 命名方式 | 示例 |
|------|----------|------|
| 用户 | 中文名，带引号 | `学生 "小林"` |
| 数值 | 阿拉伯数字 | `等级为 2`、`金币 530` |
| 状态值 | 英文代码，带引号 | `状态为 "finished"` |
| 布尔值 | 正面描述 | `已开启` / `尚未开启` |

### Step 5：审视与补全（Review & Complete）

**输入**：
- Step 4 的完整 BDD 文档

**输出**：
- 审视报告
- 补充缺失的 Scenario

**审视清单**（见第六章）：

1. 每个 Feature 是否有 Happy Path？
2. 每个校验规则是否至少有 2 个 Scenario（正常 + 异常）？
3. 涉及写入的 Scenario 是否有幂等性验证？
4. 涉及权限的是否有不同角色的 Scenario？
5. 空状态是否有处理？

### Step 6：映射到测试（Test Mapping）

**输入**：
- 审视通过的 BDD 文档

**输出**：
- 附录：BDD 到测试的映射建议

**映射规则**：

| BDD 特征 | 推荐测试类型 |
|----------|-------------|
| 纯后端业务逻辑 | 后端单元测试（Pytest） |
| API 输入输出 | API 集成测试（FastAPI TestClient） |
| 前端 UI 交互 | E2E 测试（Cypress / Playwright） |
| 前端组件独立行为 | 前端组件测试（React Testing Library） |
| 数据一致性 | DB 校验测试 |
| 并发场景 | 并发测试 / 压力测试 |

**附录格式**：

```markdown
## 附录：BDD 到测试的映射建议

| Feature | 推荐测试类型 | 优先级 |
|---------|-------------|--------|
| Feature 1 生涯模式开启 | API 单元测试 + E2E | P0 |
```

## 六、BDD 审视清单（Review Checklist）

写完 BDD 后，从以下 8 个角度审视。

### 6.1 完整性审视（Completeness）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 每个 Feature 是否有用户故事？ | As a / I want / So that 完整 |
| 2 | 每个 Feature 是否有 Happy Path？ | 至少 1 个正常流程 Scenario |
| 3 | 每个校验规则是否有对应的 Scenario？ | PRD 中的每条规则至少 1 个场景 |
| 4 | 是否覆盖空状态/空数据？ | 至少 1 个 "无数据时" 的场景 |
| 5 | 是否覆盖异常/失败场景？ | 至少 1 个错误路径场景 |
| 6 | 涉及写入的是否有幂等性场景？ | 重复操作结果一致 |

### 6.2 精确性审视（Precision）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 数据是否具体？ | 用具体数值，不用"某些""可能" |
| 2 | 状态是否明确？ | 系统状态在 Given 中完整定义 |
| 3 | 结果是否可验证？ | 每个 Then 都能写出断言语句 |
| 4 | 边界值是否精确？ | 用等号表达的边界（如"刚好等于上限"） |

### 6.3 独立性审视（Independence）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | Scenario 之间是否无依赖？ | 乱序执行也能通过 |
| 2 | Given 是否完整准备状态？ | 不依赖其他 Scenario 的副作用 |
| 3 | Background 是否只放真正公共的条件？ | 不是公共的放各自 Scenario 中 |

### 6.4 语言规范审视（Language）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 是否使用业务语言？ | 非技术人员能读懂 |
| 2 | 是否避免技术术语？ | 没有 API/数据库/HTTP 等技术词汇 |
| 3 | 术语是否与 PRD 一致？ | 与 `00-TERMINOLOGY.md` 对齐 |
| 4 | 缩写是否首次展开？ | 首次出现的缩写有全称 |
| 5 | Given 是否用完成时？ | `已开启` `已获得` 等 |
| 6 | When 是否只有一个动作？ | 一个 Scenario 一个 When |

### 6.5 可自动化审视（Automatability）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 每个 Then 是否能转化为断言？ | 有明确的期望值 |
| 2 | Given 是否能通过代码准备？ | 状态可以通过测试固件（fixture）构造 |
| 3 | When 是否能通过代码触发？ | 动作可以模拟或调用 |
| 4 | 是否有模糊的形容词？ | 没有"很快""很多""正常"等模糊词 |

### 6.6 场景粒度审视（Granularity）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 一个 Scenario 是否只测一个行为？ | 单一职责原则 |
| 2 | Scenario 步骤是否 <= 10 步？ | 过长说明场景过于复杂，应拆分 |
| 3 | Given 步骤是否 <= 5 步？ | 过多前置条件说明准备过于复杂 |
| 4 | Feature 是否 <= 8 个 Scenario？ | 过多说明 Feature 过大，应拆分 |

### 6.7 一致性审视（Consistency）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 同一角色名称是否全文一致？ | 如始终用"小林"不用"小明" |
| 2 | 同一概念用语是否一致？ | 如始终用"金币"不用"金币数" |
| 3 | 数值单位是否统一？ | 如始终用"万"或始终用原值 |
| 4 | 状态值拼写是否一致？ | 如始终用 `"finished"` 不用 `"completed"` |

### 6.8 业务价值审视（Business Value）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 用户故事是否描述了明确价值？ | So that 有具体的用户收益 |
| 2 | 场景是否覆盖了用户关心的结果？ | 不是只覆盖系统内部行为 |
| 3 | 场景是否遗漏了关键业务规则？ | 与 PRD 逐条对照 |
| 4 | 场景是否反映了真实使用场景？ | 场景在真实使用中会发生 |

## 七、常见错误与避坑指南

### 7.1 语法层面

| 错误 | ❌ 反例 | ✅ 正例 | 后果 |
|------|---------|---------|------|
| Given 写动作 | `Given 用户点击登录按钮` | `Given 用户已登录` | 将触发动作与前置状态混淆 |
| When 多个动作 | `When 用户输入密码并点击登录` | `When 用户提交登录表单` | 一个场景测试多个行为 |
| Then 写实现 | `Then 数据库插入一条记录` | `Then 用户获得金币 30` | 暴露了实现细节，重构时场景失效 |
| 模糊数据 | `Then 用户获得一些金币` | `Then 用户获得金币 30` | 无法验证对错 |
| 被动语态 | `Then 金币被发放给用户` | `Then 用户获得金币 30` | 主语不明确 |
| 技术术语 | `When 发送 POST 请求` | `When 玩家提交买入决策` | 业务人员看不懂 |

### 7.2 结构层面

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| Scenario 之间共享状态 | 乱序执行失败 | 每个 Scenario 的 Given 准备完整状态 |
| Feature 过大（>10 个 Scenario） | 难以阅读和维护 | 拆分为多个 Feature |
| 缺少用户故事 | 读者不知道这个功能为谁服务 | 每个 Feature 必须写 As a / I want / So that |
| 缺少 Background | 大量重复的 Given | 提取公共 Given 到 Background |
| Background 过于复杂 | 隐藏了 Scenario 的真实前提 | Background 只放最简单的公共条件 |

### 7.3 内容层面

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 只写 Happy Path | 线上异常频发 | 每个操作至少写正常 + 异常两个场景 |
| 遗漏幂等性 | 重复操作导致数据错误 | 涉及写入必须写幂等场景 |
| 遗漏空状态 | 空数据时页面崩溃 | 写"无数据时"的场景 |
| 数据不一致 | 前后端数据展示不同 | 写数据一致性验证场景 |
| 场景标题不清晰 | 维护者不知道测什么 | 标题包含条件和期望结果 |

### 7.4 与 PRD 的对齐

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| BDD 与 PRD 规则不一致 | 开发和测试标准不同 | 写 BDD 时逐条对照 PRD |
| BDD 超前于 PRD | PRD 变更后 BDD 失效 | PRD 定稿后再写 BDD |
| BDD 遗漏 PRD 规则 | 功能缺失 | 用 PRD 规则清单逐一检查覆盖度 |
| 术语不一致 | 理解偏差 | 使用 `00-TERMINOLOGY.md` 统一术语 |

## 九、商识唯智 BDD 写作最佳实践

### 9.1 命名规范

| 项目 | 规范 | 示例 |
|------|------|------|
| 用户名称 | 中文名，带引号 | `"小林"` `"小王"` |
| 数值 | 阿拉伯数字，单位明确 | `金币 530` `XP 100` |
| 状态值 | 英文代码，小写，带引号 | `"finished"` `"playing"` `"draft"` |
| 枚举值 | 英文大写，带引号 | `"TECH"` `"USER"` `"BRAND"` |
| 页面元素 | 中文，用「」标注 | `「开启生涯」按钮` |
| 提示文本 | 原文引用 | `"数据同步中，部分信息可能不是最新"` |

### 9.2 数值处理

- **精确计算的结果**：写出计算公式
  ```gherkin
  Then 小林获得金币 38（30 × 1.25 取整）
  ```
- **固定值**：直接写出
  ```gherkin
  Then 小林获得钻石 2
  ```
- **范围值**：写出范围
  ```gherkin
  Then 小林获得金币在 20 到 50 之间
  ```
- **零值**：明确写出 0
  ```gherkin
  Then 小林获得钻石 0
  ```

### 9.3 状态引用

引用系统状态时，使用完成时态 + 具体值：

```gherkin
Given 小林的等级为 2
And 小林的 XP 为 100
And 小林的金币为 530
```

而非：

```gherkin
❌ Given 小林有等级
❌ Given 小林有一些 XP
```

### 9.4 条件叠加

多个条件用 `And` 连接，保持层级清晰：

```gherkin
Given 学生 "小林" 已注册并登录
And 小林尚未开启生涯模式
And 小林的网络连接正常
```

超过 5 个 Given 时，考虑使用 Background 或简化条件。

### 9.5 负面验证

使用 `But` 或明确的否定语句进行负面验证：

```gherkin
Then 小林获得金币 30
And 小林不获得钻石
But 页面不发生跳转
```

## 十、BDD 与 PRD 的协同工作流

### 10.1 标准工作流

```
Phase 1：PRD 撰写
  └── 产品经理完成 PRD 初稿
      └── 开发负责人技术评审
          └── PRD 定稿（🟢 状态）
              ↓
Phase 2：BDD 生成
  └── 基于定稿 PRD 生成 BDD
      └── 开发、QA、产品三方评审
          └── BDD 定稿
              ↓
Phase 3：开发
  └── 开发人员参考 BDD 编写代码
      └── 每完成一个 Feature，自测对应 Scenario
          └── 开发完成
              ↓
Phase 4：测试
  └── QA 将 BDD 转化为自动化测试
      └── 执行测试
          └── 测试通过 = 验收通过
              ↓
Phase 5：维护
  └── 需求变更 → 更新 PRD → 更新 BDD → 更新测试
```

### 10.2 变更管理

| 变更类型 | PRD | BDD | 测试 |
|----------|-----|-----|------|
| 新增功能 | 更新 | 新增 Feature | 新增测试 |
| 修改规则 | 更新 | 修改对应 Scenario | 修改测试 |
| 删除功能 | 删除章节 | 删除 Feature 或标记废弃 | 删除测试 |
| Bug 修复 | 一般不变 | 新增回归 Scenario | 新增回归测试 |

### 10.3 文档同步原则

1. **PRD 是源头**：PRD 变更后，必须同步更新 BDD
2. **BDD 是契约**：BDD 定稿后，开发以此为准
3. **测试是保障**：自动化测试覆盖所有 BDD Scenario
4. **三方确认**：PRD 和 BDD 的变更需产品、开发、QA 三方确认

## 附录：Gherkin 语法速查卡

```gherkin
# 文件结构
Feature: [功能名称]

  [用户故事：As a / I want / So that]

  Background:
    Given [公共前置条件]

  Scenario: [场景描述]
    Given [前置状态]
    And [前置状态补充]
    When [触发事件]
    Then [预期结果]
    And [结果补充]
    But [反向结果]

  Scenario Outline: [参数化场景]
    Given [前置状态]
    When [事件] <参数>
    Then [结果] <预期>

    Examples:
      | 参数 | 预期 |
      | A    | X    |
      | B    | Y    |
```

**关键字优先级**：

```
Feature（每个文件一个）
  └── Background（可选，一个）
  └── Scenario / Scenario Outline（多个）
        └── Given（多个，用 And/But 连接）
        └── When（一个）
        └── Then（多个，用 And/But 连接）
```

**步骤类型规则**：

| 步骤 | 时态 | 数量 | 示例 |
|------|------|------|------|
| Given | 完成时 | 1~5 个 | `Given 小林已登录` |
| When | 一般现在时 | 1 个 | `When 小林提交决策` |
| Then | 一般现在时 | 1~5 个 | `Then 小林获得金币 30` |
