# 人机交互协议

> **文档定位**：定义学生（人类管理者）与 AI 员工之间的完整交互协议，覆盖任务全生命周期——从需求下发到最终验收。本文档是 OPC 平台人机协作引擎的实现规范。
>
> **关联文档**：`02-系统Prompt设计.md`、`03-技能升级与绩效系统.md`
>
> **最后更新**：2026-05-17

---

## 一、协议总则

### 1.1 交互模型

OPC 采用**"管理者-执行者"**模型，而非传统的**"用户-助手"**模型：

```
传统 AI 交互                    OPC 人机交互
┌─────────────────┐            ┌─────────────────────────────┐
│ 用户提问        │            │ 学生派发任务（结构化需求）    │
│ AI 即时回答     │     →→→    │ AI 员工执行（异步/实时）      │
│ 对话结束        │            │ 学生验收交付物               │
│                 │            │ 评分反馈 → 迭代或归档        │
└─────────────────┘            └─────────────────────────────┘
```

### 1.2 核心原则

| 原则 | 描述 | 对学生的影响 | 对 AI 员工的影响 |
|------|------|-------------|----------------|
| **任务驱动** | 所有交互以任务为单位组织 | 必须清晰表达需求 | 必须结构化输出交付物 |
| **异步为主** | 复杂任务允许异步执行 | 无需实时等待 | 可在后台并行处理 |
| **透明可见** | 执行过程对学生完全透明 | 可随时查看进度 | 必须实时上报状态 |
| **验收把关** | 学生拥有最终验收权 | 必须认真评审 | 必须接受反馈并修改 |
| **迭代优化** | 支持多轮改进 | 提供具体反馈 | 基于反馈精准调整 |

### 1.3 通信协议栈

```
┌─────────────────────────────────────────────┐
│ 应用层：任务语义（需求描述、交付标准）          │
├─────────────────────────────────────────────┤
│ 会话层：对话上下文（记忆检索、角色状态）        │
├─────────────────────────────────────────────┤
│ 传输层：消息格式（JSON Schema、事件流）         │
├─────────────────────────────────────────────┤
│ 安全层：权限校验（MCP 授权、伦理审核）          │
└─────────────────────────────────────────────┘
```

## 二、任务派发格式

### 2.1 任务创建接口

学生创建任务时，系统提供结构化模板，同时支持自然语言输入（由 Cortex 自动解析为结构化需求）。

#### 2.1.1 标准任务模板（YAML）

```yaml
task_spec:
  # 基础信息
  task_id: "T-20260517-001"
  title: "竞品分析报告"
  created_by: "student_001"
  created_at: "2026-05-17T09:00:00+08:00"
  
  # 指派信息
  assignee:
    codename: "BA-01"
    name: "商业分析师"
    auto_assign_reason: "基于任务类型自动匹配"  # 若学生手动指定则为 null
  
  # 需求描述（核心）
  requirement:
    context: |
      我正在做一个面向大学生的时间管理 App，
      需要了解市场上的主要竞品情况。
    objective: "识别 Top 5 竞品，分析其核心功能和差异化策略"
    scope:
      include: ["功能对比", "定价策略", "用户评价", "目标人群"]
      exclude: ["技术架构", "融资历史"]
    constraints:
      - "预算相关：仅需免费版/低价版功能"
      - "时间范围：近 2 年内的产品"
      - "地域范围：中国大陆市场为主"
    success_criteria:
      - "列出至少 5 个竞品"
      - "每个竞品有功能矩阵评分"
      - "识别出至少 2 个差异化机会点"
    
  # 交付标准
  deliverable:
    format: "markdown_report"  # 可选：markdown | json | figma | code | image | mixed
    template: "competitor_analysis_v2"  # 使用预设模板
    sections_required:
      - "执行摘要"
      - "竞品概览"
      - "功能对比矩阵"
      - "差异化分析"
      - "建议下一步"
    review_checklist:
      - "数据是否有来源标注？"
      - "对比维度是否一致？"
      - "是否包含可验证的结论？"
  
  # 时间约束
  timeline:
    priority: "P1"  # P0=紧急, P1=重要, P2=常规
    expected_start: "2026-05-17T09:00:00+08:00"
    expected_completion: "2026-05-17T18:00:00+08:00"
    deadline_flexibility: "strict | flexible | best_effort"
    
  # 资源与权限
  resources:
    budget_simulated: 0  # 模拟币预算
    budget_real: 0       # 真实货币预算（如需付费工具）
    mcp_tools_authorized:
      - "google-search"
      - "spreadsheet"
      - "OPC-atlas"
    memory_access:
      - "project_time_mgmt_app"
      - "previous_research_20260510"
    
  # 协作要求
  collaboration:
    requires_input_from: []  # 执行中是否需要其他员工输入
    notify_on_completion: ["Cortex"]
    student_checkpoints:
      - at: "30%"
        action: "提交初步竞品列表，等待学生确认方向"
      - at: "70%"
        action: "提交分析框架，等待学生确认深度"
  
  # 元数据
  meta:
    estimated_effort: "4-6小时"
    difficulty: "medium"
    skill_tags: ["竞品分析", "市场调研"]
    expected_xp: 300
```

#### 2.1.2 自然语言解析流程

```json
{
  "natural_language_input": "BA-01，帮我分析一下做时间管理 App 的竞争对手，主要看看他们有什么功能、怎么收费的，还有用户对他们评价怎么样。最好今天能给我。",
  
  "cortex_parsing": {
    "detected_intent": "competitor_analysis",
    "confidence": 0.95,
    "extracted_entities": {
      "product_domain": "时间管理 App",
      "target_market": "未明确（默认中国大陆）",
      "focus_areas": ["功能", "定价", "用户评价"],
      "deadline": "今日"
    },
    "ambiguities": [
      {
        "field": "target_market",
        "question": "你希望重点关注哪个地区的市场？",
        "default": "中国大陆"
      },
      {
        "field": "competitor_scope",
        "question": "竞品数量上限是多少？",
        "default": "Top 5"
      }
    ],
    "proposed_task_spec": "...（自动生成的 YAML，学生可编辑确认）"
  }
}
```

#### 2.1.3 任务确认流程

```
学生输入需求
    │
    ▼
Cortex 解析 → 生成结构化任务草案
    │
    ▼
学生审阅并编辑（可修改指派、时间、范围）
    │
    ├── 确认 → 下发给 AI 员工
    │
    └── 取消/暂存 → 存入草稿箱
```

### 2.2 任务下发事件

```json
{
  "event_type": "task.assigned",
  "timestamp": "2026-05-17T09:05:00+08:00",
  "payload": {
    "task_id": "T-20260517-001",
    "assignee": "BA-01",
    "task_spec": { "..." },
    "agent_context": {
      "current_workload": 2,
      "current_status": "standby",
      "estimated_available_at": "2026-05-17T09:05:00+08:00"
    }
  },
  "agent_response": {
    "status": "accepted",
    "estimated_start": "2026-05-17T09:05:00+08:00",
    "estimated_completion": "2026-05-17T16:00:00+08:00",
    "clarification_requests": [],
    "risk_flags": []
  }
}
```

AI 员工收到任务后，必须在 30 秒内响应：
- **Accepted**：接受任务，给出预估时间
- **Clarification Needed**：需求存在歧义，列出需澄清的问题
- **Rejected**：因能力/负载/权限原因无法接受，说明原因
- **Delegated**：建议转派给其他更适合的 AI 员工

## 三、执行状态上报格式

### 3.1 状态机定义

```
[待启动] ──▶ [分析中] ──▶ [执行中] ──▶ [待验收]
   │            │           │            │
   │            ▼           ▼            ▼
   │         [等待输入] [暂停]        [修改中]
   │            │           │            │
   │            └───────────┘            │
   │                                     ▼
   └──────────────────────────────── [已完成]
                                      │
                                      ▼
                                   [已归档]
```

### 3.2 状态上报事件类型

| 事件类型 | 触发条件 | 上报频率 |
|----------|----------|----------|
| `task.started` | 任务开始执行 | 单次 |
| `task.progress` | 进度更新 | 每 10% 或每 30 分钟 |
| `task.checkpoint` | 到达预设检查点 | 按任务定义 |
| `task.blocked` | 遇到阻塞 | 即时 |
| `task.input_needed` | 需要学生输入 | 即时 |
| `task.completed` | 任务完成，交付物就绪 | 单次 |
| `task.paused` | 任务暂停 | 即时 |
| `task.resumed` | 任务恢复 | 即时 |
| `task.cancelled` | 任务取消 | 单次 |

**修改轮次限制**：
- 每个任务最多允许 3 轮修改请求
- 超过 3 轮后，Cortex 自动介入分析根因（需求不清晰 vs 执行偏差）
- 若判定为需求不清晰，任务可重新拆解，不惩罚 AI 员工绩效

## 五、中断与暂停机制

### 5.1 学生侧操作

| 操作 | 触发条件 | 效果 | 恢复方式 |
|------|----------|------|----------|
| **暂停** | 学生手动点击暂停 | 任务挂起，状态保存，AI 员工进入待机 | 学生点击恢复 |
| **取消** | 学生决定不再需要该任务 | 任务终止，已产出部分可查看，不发放 XP | 不可恢复，可重新创建 |
| **加急** | 学生提升优先级 | 若 AI 员工有多个任务，插队执行 | 自动生效 |
| **改派** | 学生认为当前员工不适合 | 当前任务终止，转派给新员工 | 新任务创建 |
| **介入指导** | 学生想实时指导执行 | 触发"协同模式"，学生可实时看到 AI 思考过程 | 学生退出协同模式 |

### 5.2 暂停事件格式

```json
{
  "event_type": "task.paused",
  "triggered_by": "student",
  "payload": {
    "task_id": "T-20260517-001",
    "agent_codename": "BA-01",
    "pause_reason": "学生手动暂停",
    "state_snapshot": {
      "progress_percentage": 45,
      "phase": "data_collection",
      "intermediate_results": "...",
      "memory_context": "..."
    },
    "auto_resume": {
      "enabled": false,
      "scheduled_at": null
    },
    "notification": {
      "message": "任务已暂停。BA-01 已保存当前进度，恢复后可继续执行。",
      "to": ["student", "Cortex"]
    }
  }
}
```

### 5.3 AI 员工侧自我保护

AI 员工在以下情况下可主动请求暂停：

```yaml

    action: "暂停执行，请求学生授权"
    
  - condition: "检测到潜在的安全或伦理风险"

  - condition: "执行时间超出预估 200%"
    action: "暂停执行，说明原因并请求是否继续"
    
  - condition: "学生设定的检查点未通过（30%/70%）"
    action: "暂停等待学生确认，再继续"
```

## 六、多轮迭代工作流程

### 6.1 标准迭代周期（Sprint 模式）

```yaml
sprint_cycle:
  duration: "1 周"
  
  day_1_planning:
    - actor: "学生 + Cortex"
    - action: "回顾上周成果，设定本周目标"
    - output: "sprint_plan.json"
    
  day_2_4_execution:
    - actor: "AI 员工团队"
    - action: "并行执行任务"
    - checkpoint: "每日 17:00 自动进度同步"
    
  day_5_integration:
    - actor: "AI 员工 + 学生"
    - action: "集成测试与初步验收"
    - output: "集成测试报告"
    
  day_6_review:
    - actor: "学生"
    - action: "验收本周交付物，填写评审"
    - output: "performance_reviews"
    
  day_7_deployment:
    - actor: "DEV-01 + OPS-01"
    - action: "部署到生产/预览环境"
    - output: "deployment_log"
    
  day_7_retrospective:
    - actor: "学生 + Cortex + 全体 AI 员工"
    - action: "复盘本周：什么做得好？什么可以改进？"
    - output: "sprint_retrospective.md"
```

### 6.2 快速迭代模式（Quick Loop）

适用于小修改、高频率场景（如文案调整、UI 微调）：

```
学生提出修改需求（自然语言，< 50 字）
    │
    ▼
AI 员工确认理解（10 秒内）
    │
    ▼
AI 员工执行修改（< 30 分钟）
    │
    ▼
学生即时预览
    │
    ├── 满意 → 确认 → 自动归档
    │
    └── 不满意 → 继续修改（同流程）
```

**快速迭代限制**：
- 每次修改范围 ≤ 原交付物的 20%
- 同一任务的快速迭代上限 10 次
- 超过 10 次后，Cortex 建议重新下发结构化任务

### 6.3 深度迭代模式（Deep Dive）

适用于复杂、长周期的任务（如产品重构、品牌战略升级）：

```yaml
deep_dive_mode:
  phases:
    - name: "调研阶段"
      duration: "3-5 天"
      deliverable: "调研报告 + 方案选项"
      gate: "学生选择方向"
      
    - name: "方案阶段"
      duration: "5-7 天"
      deliverable: "详细方案 + 原型/草稿"
      gate: "学生评审并提出修改"
      
    - name: "执行阶段"
      duration: "7-14 天"
      deliverable: "完整交付物"
      gate: "验收测试"
      
    - name: "优化阶段"
      duration: "3-5 天"
      deliverable: "优化版本"
      gate: "最终验收"
  
  governance:
    - "每个阶段结束时必须验收才能进入下一阶段"
    - "阶段内修改不占用修改轮次"
    - "学生可随时调用 Cortex 评估是否需要调整阶段计划"
```

## 七、冲突解决机制

### 7.1 冲突类型定义

| 冲突类型 | 描述 | 示例 |
|----------|------|------|
| **意见冲突** | 两个 AI 员工对同一问题给出不同建议 | DEV-01 建议用 React，DES-01 建议用 Vue |
| **资源冲突** | 多个任务争夺有限资源 | 预算限制下，GRW-01 和 COPY-01 都需要付费工具 |
| **依赖冲突** | 任务 A 依赖任务 B，但 B 延迟 | DES-01 的设计稿延迟，阻塞 DEV-01 开发 |
| **优先级冲突** | 学生指派了超出负载的任务 | 同时要求 BA-01 完成 3 个 hard 任务 |
| **数据冲突** | 不同来源的数据结论矛盾 | Scout 的用户反馈与 UR-01 的访谈结论不一致 |

## 八、异常处理与降级策略

### 8.1 学生侧异常

| 异常场景 | 系统响应 | 学生引导 |
|----------|----------|----------|
| 学生表达需求不清晰 | Cortex 生成澄清问题列表 | "为了给你最好的结果，我需要确认以下几点..." |
| 学生要求超出 AI 能力 | 明确告知边界并提供替代方案 | "这个任务超出了我目前的能力，但我可以..." |
| 学生连续取消任务 | Cortex 主动沟通了解原因 | "我注意到你最近取消了几个任务，有什么我可以调整的吗？" |
| 学生长时间不响应 | 自动提醒（3天/7天/14天） | "这个任务还在等待你的反馈，需要我调整什么吗？" |
| 学生表达挫败/负面情绪 | 触发情感支持协议 + 导师通知 | "创业确实不容易，这个卡点我们可以一起想办法..." |

### 8.2 AI 员工侧异常

| 异常场景 | 系统响应 | 上报路径 |
|----------|----------|----------|
| AI 生成内容触发安全审核 | 立即停止，内容隔离 | OPC-ethos → 学生通知 |
| AI 工具调用失败 | 自动重试 3 次，然后上报 | Cortex → 学生 |
| AI 执行时间超时 | 强制暂停，保存状态 | Cortex → 学生 |
| AI 输出质量持续下降 | 触发绩效预警机制 | Cortex → 学生 → 再培训 |
| AI 产生幻觉/错误数据 | 标记置信度低，要求复核 | 自动标注 → 学生确认 |

### 8.3 系统级故障

```yaml
system_fault_handling:
  llm_service_unavailable:
    detection: "LLM API 响应超时或返回错误"
    response:
      - "自动切换到备用模型（降级服务）"
      - "通知学生：当前使用备用模型，部分高级功能暂不可用"
      - "主服务恢复后自动切换回主模型"
    
  mcp_server_down:
    detection: "MCP Server 连接失败"

      - "标记该工具为不可用"

  database_corruption:
    detection: "数据一致性检查失败"

      - "立即冻结相关 AI 员工"
      - "从最近备份恢复"
      - "通知平台运营团队"
```

## 九、通知与沟通协议

### 9.1 通知分级

| 级别 | 场景 | 渠道 | 响应要求 |
|------|------|------|----------|
| **紧急** | 安全风险、资金异常、系统故障 | App Push + 短信 + 邮件 | 立即 |
| **重要** | 任务完成、里程碑达成、冲突需要决策 | App Push + 邮件 | 4 小时内 |
| **常规** | 进度更新、日报、周会提醒 | App 内消息 | 24 小时内 |
| **低优先级** | 学习资源推荐、成就解锁 | App 内消息（可聚合） | 无需响应 |

### 9.2 批量通知策略

```yaml
notification_batching:
  rule: "同一 Agent 的多个常规通知在 1 小时内聚合为一条"
  example:
    raw: [
      "BA-01: 任务 T001 进度 20%",
      "BA-01: 任务 T001 进度 40%",
      "BA-01: 任务 T001 进度 60%"
    ]
    batched: "BA-01 正在执行 T001，当前进度 60%，预计 2 小时后完成"
```

### 9.3 学生免打扰模式

```yaml
do_not_disturb:
  modes:
    - name: "专注模式"
      blocks: ["常规", "低优先级"]
      allows: ["紧急", "重要"]
      auto_reply: "学生当前处于专注模式，你的任务正常执行中，非紧急事项将在模式结束后统一通知。"
      
    - name: "睡眠模式"
      schedule: "22:00 - 08:00"
      blocks: ["常规", "低优先级", "重要（非紧急）"]
      allows: ["紧急"]
      
    - name: "考试模式"
      duration: "学生自定义"
      blocks: ["所有通知"]
      allows: ["紧急安全事件"]
      background_execution: true  # AI 员工继续执行，只是不通知
```
