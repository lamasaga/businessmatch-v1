## 二、查漏补缺：问题清单与风险评级

### 🔴 P0 — 阻塞级遗漏（必须在开发前补齐）

#### P0-1: Gateway 评审评分算法缺失

| 项目 | 详情 |
|------|------|
| **现状** | `database-api-specs/01-完整数据库Schema.md` 定义了 `GatewayReview` 表，`venture-playbook/` 各阶段有 Gateway 通过标准描述，但**没有专门的算法/逻辑设计文档**。 |
| **风险** | Gateway 是"模拟→真实"的核心阀门。没有算法设计，开发团队无法确定：评分维度如何加权？AI 评审 vs 导师评审 vs 同伴评审如何合成？条件通过（CONDITIONAL）的触发逻辑是什么？ |
| **应补内容** | 独立的 `gateway-evaluation/01-Gateway评审算法设计.md`，包含：评审维度矩阵（每个阶段的评分项、权重）、多评审者合成算法（AI Panel 投票机制、置信度阈值）、条件通过的自动触发规则、历史数据回测框架。 |
| **建议优先级** | ⭐⭐⭐⭐⭐ 最高 |

#### P0-2: 13 个 AI 员工的完整 YAML Prompt 模板缺失

| 项目 | 详情 |
|------|------|
| **现状** | `02-系统Prompt设计.md` 定义了设计原则（角色锚定、输出格式、苏格拉底方法），`01-AI员工角色全览.md` 定义了身份和能力矩阵，但**没有可直接喂给 LLM 的系统 Prompt YAML 文件**。 |
| **风险** | 这是 AI 员工"活起来"的最关键生产资料。没有 Prompt，LangGraph 工作流只能跑空转。 |
| **应补内容** | `ai-employee-prompts/` 目录下 13 个 `.yaml` 文件，每个包含：`system_prompt`（完整系统提示词）、`tool_use_policy`（该角色可调用的 MCP 工具白名单及使用规范）、`output_schema`（该角色各类交付物的 JSON Schema）、`memory_context_template`（记忆注入模板）、`student_interaction_guardrails`（该角色特有的学生交互约束）。 |
| **建议优先级** | ⭐⭐⭐⭐⭐ 最高 |

#### P0-3: 成本与配额控制设计缺失

| 项目 | 详情 |
|------|------|
| **现状** | 文档中多次提到 LLM 调用、沙箱运行、向量检索，但**没有任何关于成本控制和学生配额限制的设计**。 |
| **风险** | 这是商业化可行性问题。一个学生如果让 AI 员工无限循环执行任务，LLM Token 消耗可能单日破百元。没有配额 = 没有商业模式。 |
| **应补内容** | `operations/01-成本结构与配额设计.md`，包含：LLM 调用成本模型（按任务类型估算 Token 消耗）、沙箱运行时长配额、存储配额（向量 DB + 文件）、学生月度/学期配额包设计（免费额度 + 付费升级）、配额耗尽时的优雅降级策略（切换到 cheaper 模型、减少 MCP 调用频率）。 |
| **建议优先级** | ⭐⭐⭐⭐⭐ 最高 |

## 三、一致性隐患：文档间的潜在冲突

### 3.1 AI 员工角色代号不一致

**发现**：不同文档中对同一角色的引用存在差异：
- `01-AI员工角色全览.md`：使用 `BA-01`、`DEV-01` 等代号
- `04-人机交互协议.md`：使用 `BA-01`、同时出现 `Scout`（侦察员）、`UR-01`（用户研究员）
- `venture-playbook/`：使用 `BA-01`、`CP-01`（创意策划师）

**问题**：`CP-01` 和 `UR-01` 在 `01-AI员工角色全览.md` 的 13 个角色中**不存在**，它们是新出现的角色。

**建议**：
1. 明确 13 个角色的冻结列表（canonical list）
2. 如果 `CP-01`、`UR-01`、`Scout` 是需要的，更新 `01-AI员工角色全览.md` 将其纳入
3. 或者统一使用更通用的代号体系（如 `BA-01` = 商业分析师，`SCT-01` = 侦察员）

### 3.2 公司阶段定义不一致

**发现**：
- `database-api-specs/01-完整数据库Schema.md`：`CompanyStage` = IDEATE | VALIDATE | BUILD | LAUNCH | SCALE | ARCHIVED
- `venture-playbook/`：5 个阶段（IDEATE → VALIDATE → BUILD → LAUNCH → SCALE），但没有 ARCHIVED
- `code-skeleton/02-SQLAlchemy模型骨架.py`：与 Schema 一致

**问题**：ARCHIVED 状态在 SOP 中没有对应的操作手册。学生如何归档公司？归档后数据如何处理？AI 员工是否解散？

**建议**：补充 `venture-playbook/06-ARCHIVE阶段SOP.md` 或在现有 SOP 中增加归档流程。

## 六、关键决策建议

### 决策 1: LLM 供应商策略

**建议**：采用"**主模型 + 备用模型 + 降级模型**"的三层策略：
- **主模型**：Claude 3.5 Sonnet（推理能力强，适合复杂商业分析）
- **备用模型**：GPT-4o（速度快，适合代码生成和实时交互）
- **降级模型**：GPT-4o-mini（配额耗尽或主服务故障时自动切换）

**理由**：单一供应商锁定的风险和成本都过高。Claude 在长文本和结构化输出上更稳定，GPT-4o 在代码任务上更快。

### 决策 2: 沙箱方案选择

**建议**：MVP 阶段使用 **nsjail + Docker**（开发快、易调试），生产环境迁移到 **gVisor**（安全强）。

**理由**：gVisor 的 setup 复杂度高，MVP 阶段不应被基础设施阻塞。nsjail 提供了足够的隔离（命名空间 + seccomp），且启动速度快，适合教学场景的高频短任务。

### 决策 3: 多人协作优先级

**建议**：**v1.0 之后再考虑多人协作**。

**理由**："一人公司"的核心叙事是单人 + AI 团队。加入多人协作会大幅增加复杂度（权限、冲突、版本合并）。先验证单人模式的产品价值，再扩展。

### 决策 4: 真实支付的时间点

**建议**：真实支付**不绑定 LAUNCH 阶段**，而是作为可选的"进阶挑战"。

**理由**：涉及真实货币的合规要求极高（支付牌照、税务、未成年保护）。早期应允许学生在"测试用户"阶段获得完整体验，真实支付作为"毕业后"的额外成就，而非必经之路。

## 七、结语

OHB 模块已经从一个创意概念成长为**具备完整技术规格、可运行代码骨架、详细运营手册**的严肃产品方案。40+ 文档、150,000+ 字的投入，意味着我们已经跨过了"想清楚"的阶段，进入了"做出来"的阶段。

当前最紧迫的三件事：
1. **写 Prompt** — 13 个 AI 员工的系统 Prompt 是产品灵魂，必须立即启动
2. **定算法** — Gateway 评审评分算法是"模拟→真实"的阀门，必须在开发前冻结
3. **控成本** — 没有配额设计，再好的产品也无法规模化运营

这三件事完成后，开发团队可以沿着"数据库 → API → 前端 → AI 集成 → 沙箱"的顺序逐步推进，每一步都有明确的文档依据和验收标准。

**OHB 的愿景是让每个学生都能运营一家真实的一人公司。现在，我们距离实现这个愿景，还差一个高质量的 Prompt、一个严谨的算法、一行行的代码。**
