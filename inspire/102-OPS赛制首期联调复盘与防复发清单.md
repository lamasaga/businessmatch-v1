## 零、读者与本文价值

　　2026-06 初，OPS（生产经营销售赛，`ops_sim`）完成学生练习入口与教师控场页的首轮贯通联调。表面现象是：学生端「确认定位」后界面不推进、教师端控场页黑屏；Network 面板里部分请求返回 **200**，容易误判为「前端没发请求」或「后端已正常」。

　　本文记录**一次真实联调中暴露的多层根因**，并整理为**可复用的防复发清单**，供后续新增赛制、双端页面或练习/正式分流时对照。读者对象：主理人、全栈与 AI 编程会话——不必重复踩「契约不一致 + 练习流未分叉 + 旧进程仍在监听」的组合坑。

---

## 一、现象摘要（What 用户看到了）

| 端 | 现象 | 控制台 / Network 线索 |
|----|------|------------------------|
| **学生端** | 产品定位页可填写，点「确认定位」后仍停在定位阶段 | 后期可见 `product-positioning` 与 `state` 均为 **200**，且成对重复出现 |
| **教师端** | 新建 OPS 赛事进入控场页后**黑屏** | `OpsControlPage.tsx` 报错：`Cannot read properties of undefined (reading 'length')` |
| **次要噪音** | 教师端 `401 /auth/me`、`422 teaching-groups/.../pending-count` | 与 OPS 主链路无直接关系（登录过期、体验营接口参数不匹配） |

　　值得强调：**HTTP 200 不等于业务状态已推进**。学生端多次 200 的 `product-positioning`，恰恰是「提交成功但 `phase` 仍为 `positioning`」时，用户反复点击产生的症状，而非请求未发出。

---

## 二、根因链（Why 会同时坏在两端）

### 2.1 教师端黑屏：API 契约窄于前端假设

　　教师控场页 `OpsControlPage` 调用 `GET /api/v1/ops/events/{id}/screen`，期望拿到**完整控场快照**：`teams`、`rounds`、`participant_count`、`room_code`、`ranking` 等。首期实现中，`screen` 仅返回 `{ match_status, phase, ranking }` 三个字段。

　　前端直接访问 `state.teams.length`，在 `teams === undefined` 时 React 渲染崩溃，整页黑屏。这是典型的 **「前后端契约未在联调前写清 + 前端无防御性默认值」** 叠加问题；与认证 401 无关——`screen` 若已 200，缺字段一样会崩。

### 2.2 学生端卡住：练习赛误用「全员提交才推进」的正式赛规则

　　OPS 产品定位阶段的设计是：各队提交产品卡后，全场进入运营第 1 轮（R1）。正式赛逻辑为：`submitted >= total_teams` 时推进。

　　**日常练习**由 `POST /api/v1/practice/ops/start` 创建，结构为 **1 名人类 + N 支 AI 队**（默认 3 支）。人类提交后 `submitted = 1`，`total_teams = 4`，条件永不满足，`ops_phase` 一直停在 `positioning`。AI 队不会走学生端 UI 提交定位，必须由后端在练习流中**自动填位**或教师端**推进阶段**。

　　根因归类：**`match_kind = practice` 与 `official` 的分流未在定位推进处落地**，属于赛制生命周期设计疏漏，而非单个字段校验错误。

### 2.3 改码已合并但行为仍旧：Windows 下后端无热重载 + 旧进程残留

　　`webapp/backend/run.py` 刻意设置 `reload=False`（注释说明：Windows 下 reload 易残留多监听进程，浏览器仍打到旧代码）。联调期间本地已修改 `ops.py`，但 **:8000 上跑的仍是启动时的旧进程**。

　　表现高度迷惑：

- `product-positioning` 返回 **200**（旧逻辑：只存卡，不推进）
- 响应体**没有** `phase` 字段（新逻辑才返回）
- 紧接着 `state` 的 `phase` 仍为 `positioning`
- 用户多次点击 → Network 里成批重复的 200

　　这是本次排查中**最容易被「全绿 Network」误导**的一环：必须用**响应 JSON 语义**或**重启后冒烟脚本**验证，不能只看状态码。

### 2.4 配置 JSON 持久化纪律（潜在风险，已纳入修复）

　　`ArenaMatch.config` 存 `ops_phase` 等运行时状态。项目内 RTS 等模块已通过 `persist_match_config()`（`domains/arena/config_json.py`）写入并 `flag_modified`，避免 SQLAlchemy 对 JSON **就地修改不跟踪** 的问题。OPS 首期多处使用 `match.config = {**...}` 赋值；全量赋值通常可跟踪，但与仓库纪律不一致，联调后已统一走 `persist_match_config`。

### 2.5 次要问题（记录备查，避免误当主因）

| 线索 | 说明 |
|------|------|
| 学生大厅调 `screen` | `screen` 接口带 `require_teacher`，学生端 `OpsLobbyPage` 调用会 **403**，应改用参赛端可读接口或专用 lobby 契约 |
| `game_type: 'ops'` | 建赛页曾写 `ops` 而非枚举 `ops_sim`，与 `GameEngineId` 不一致，已纠正 |
| 教师 401 | Token 过期，重新登录即可 |

## 三、修复要点（How 我们做了什么）

　　下列为联调会话内已落地的方向，具体行号以代码为准：

1. **`_screen_payload`**：组织端 `screen` 返回与控场页一致的完整结构（队伍、轮次、人数、房间码、排名等）。
2. **`_try_advance_from_positioning`**：练习赛在人类提交后 `ensure_ai_positioning`，收齐产品卡后开 R1；教师 `advance` 在定位阶段复用同一 helper。
3. **`persist_match_config`**：凡改 `ops_phase` 统一经 `config_json` 助手写入。
4. **前端防御**：`OpsControlPage` 对 `teams` / `rounds` / `ranking` 使用 `?? []`；`OpsPlayPage` 定位提交后根据 `team.category` 与响应 `phase` 切换 UI。
5. **重启后端**：杀掉旧 `python` 监听进程后，用 `venv` 内 `run.py` 重新启动，冒烟验证 `product-positioning` 响应含 `"phase": "operation_round_1"`。

## 四、防复发清单（新赛制 / 新双端页必查）

### 4.1 契约先行（联调前）

| 检查项 | 做法 |
|--------|------|
| 组织端大屏 / 控场 API | 列出前端消费的**完整字段表**，与 `GET .../screen` 或 OpenAPI 对齐；缺字段时前端必须 `??` 兜底 |
| 参赛端状态 API | `GET .../state` 的 `phase` 枚举与页面分支一一对应，写在引擎 `DESIGN.md` 或 `03-ENGINEERING` 一条 |
| 练习 vs 正式 | 凡依赖「全员提交」的逻辑，在 `match_kind == practice` 分支显式写清：AI 自动提交、单人即可推进、或专用 `practice_flow` |

### 4.2 练习赛专用流（Arena + Engine）

| 检查项 | 做法 |
|--------|------|
| AI 队初始化 | 创建练习局时同步 `OpsTeamState` + bot `ArenaParticipant` |
| 人类-only 阶段 | 定位、竞价等「每队一条」的环节，练习赛在人类动作后调用 `ensure_ai_*` |
| 响应可观测 | 改变 `phase` 的 POST 在 `data` 中返回 **`phase`**，便于 Network 一眼确认 |

### 4.3 本地开发与联调

| 检查项 | 做法 |
|--------|------|
| 改后端后 | **必须重启** `run.py`（无热重载）；怀疑多进程时用 `Get-NetTCPConnection -LocalPort 8000` 查监听 PID |
| 验证不止 200 | 对关键 POST 看 Response JSON 的 `phase` / `match_status`，或跑一条冒烟：登录 → `practice/ops/start` → `product-positioning` → `state` |
| 前后端同时刷新 | 学生端 Ctrl+F5；教师端重新登录清 401 |

### 4.4 代码纪律（与 blueprint-coding 一致）

| 检查项 | 做法 |
|--------|------|
| `match.config` 写入 | 使用 `persist_match_config`，禁止散落裸赋值 |
| 组织端专属路由 | 学生页禁止调用 `require_teacher` 接口；需要队伍列表则增参赛端只读端点 |
| 域边界 | OPS 表仅 `games/ops_sim/` + `api/ops.py`；不绕过 arena 改场次生命周期 |

### 4.5 建议补测（下一迭代）

- 后端集成测试：`practice/ops/start` → 定位 → 断言 `phase == operation_round_1` 且存在 `open` 的 round 1。
- 教师端：mock 最小 `screen` payload 与完整 payload 两种，控场页均不崩溃。
- CI 可选：`/health` 附带 git 短 SHA，联调时确认命中版本。

## 五、联调时如何读 Network（给非后端同学）

　　开发者工具 → **Network** → 勾选 **Preserve log** → 筛选 `ops` 或 `api`。

1. 点击请求行 → 右侧 **Response / 预览** 查看 JSON（不是只看 Status 列的绿色 200）。
2. 学生定位链路至少看两条：
   - `POST .../product-positioning` → 应有 `phase: "operation_round_1"`（练习赛成功路径）
   - `GET .../state` → `phase` 与上一致，`current_round.round_number === 1`
3. 右键请求 → **Copy response** 即可粘贴给协作者。

　　若 Status 全绿但 `phase` 不变，优先怀疑：**后端进程未重启** 或 **练习/正式分流未实现**，而非「前端没发请求」。

## 六、边界与不做的事

　　本文**不是** OPS 产品 PRD，不定义玩法数值与轮次规则；玩法见配置包 `webapp/backend/content/game-configs/ops-sim-v1.yaml` 及后续产品文档。

　　文中涉及的 401、422 体验营接口，不在此展开修；OPS 主链路验收应以 **学生定位 → R1 决策** 与 **教师控场页可渲染** 为 P0。

　　`inspire/` 为复盘与预防性知识，**不构成编程契约**；实现状态以 [03-ENGINEERING.md](../03-ENGINEERING.md) 与代码为准。
