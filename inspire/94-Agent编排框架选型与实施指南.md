## 一、为什么需要 Agent 编排

商域平台当前的 AI 能力由**规则引擎**和**模板驱动**两个层次构成：赛事中的 AI 对手通过 YAML 配置的策略参数驱动决策（见 `89-赛事工坊实现说明与使用指南`），赛后 Debrief 由模板化的统计摘要拼接而成。这套体系在 Phase A 和 Phase B 阶段运行良好，因为它满足三个核心要求——延迟极低、成本为零、行为完全可预测。

但规则引擎存在一个本质天花板：它只能表达**已被人类设计者编码的策略空间**，而无法处理「涌现性的教学对话」「跨模态的内容生成」「多 Agent 之间的协商博弈」。当平台进入 Phase C 的「Quest 服务与 Hermes-Debrief 规则模板」、Phase D 的「Persona 与知识图谱」、以及 Phase E 的「OPC LangGraph + MCP」时，我们需要一套更灵活、更具表达力的运行时来协调多个 AI 能力的协作。

这就是 Agent 编排（Agent Orchestration）的切入点。编排不是取代规则引擎——在交易赛的毫秒级决策中，规则引擎仍然是唯一合理的选择——而是在规则引擎之上，构建一个能够管理**对话 Agent、内容生成 Agent、分析 Agent、记忆 Agent**之间协作关系的中间层。它的核心职责是：定义谁在什么时机被调用、它们之间如何传递上下文、如何处理失败和回退、以及如何让整个过程对教研人员可解释、可调试。

## 二、Agent 编排的核心问题域

在将 Agent 编排引入商域之前，需要先厘清哪些场景真正需要编排，哪些场景应该继续坚持规则驱动。以下是四个关键问题域的分析。

### 2.1 教学对话的上下文连续性

Athena AI 教练在 Phase B 将具备基本的赛后点评能力。但当学生与 Athena 的对话跨越多个回合、涉及多个赛事类型、并需要引用历史对局中的具体决策时，简单的「单轮 prompt + 历史记录拼接」会变得脆弱。Agent 编排在这里的价值在于：**将对话状态建模为图结构**，每个节点代表一个对话阶段（问候 → 事实回顾 → 策略分析 → 行动建议 → 结束），边代表条件转移（学生追问 → 深入分析；学生消极 → 鼓励式回应）。LangGraph 的 StateGraph 模式天然适合这种场景——它不是让 LLM 自由发挥，而是在一个受控的状态机中，由编排器决定何时调用记忆检索、何时触发分析工具、何时需要教师人工介入。

### 2.2 多 NPC 之间的协作与冲突

`90-AI 对手 NPC 化与成长演化系统 PRD` 定义了六名首期 NPC 角色。在生涯模式中，这些 NPC 可能同时出现在同一个场景里——比如陈叔和李小投在「商会论坛」中就某个策略问题展开辩论，而学生作为旁观者或参与者加入对话。这种情况下，不能简单地让每个 NPC 各自独立调用 LLM，否则它们会相互矛盾、重复甚至陷入循环。编排器需要管理一个**共享上下文窗口**：定义当前轮次的发言者、维护一个「共识黑板」记录已确认的事实、并在NPC之间产生逻辑冲突时介入仲裁。这种多 Agent 协作模式在 CrewAI 的 GroupChat 和 LangGraph 的并行节点中都有成熟实现。

### 2.3 长周期任务的分解与追踪

OPC 一人公司的创业孵化流水线（见 `OPC/03-创业孵化流水线.md`）包含五个阶段：IDEATE → VALIDATE → BUILD → LAUNCH → SCALE。每个阶段内部又包含数十个具体任务，例如「生成商业画布 → 市场调研 → 竞品分析 → 最小可行产品定义」。当这些任务由 AI 员工执行时，一个任务的输出可能是下一个任务的输入，而某些任务可能需要人类确认后才能继续（如财务预算审批）。Agent 编排在这里的作用是：**将工作流建模为有向图，支持暂停等待人工输入、错误回滚到前一个检查点、以及任务执行状态的持久化**。这正是 LangGraph 的持久化和中断恢复机制的设计目标。

### 2.4 工具调用的标准化与可扩展性

MCP（Model Context Protocol）的引入（Phase E 规划）意味着平台上的 AI 能力将从「内置函数调用」演进为「可插拔的工具服务」。赛事引擎、数据库、外部 API（如财务软件、设计工具）都将以 MCP Server 的形式暴露给 Agent。但 MCP 只定义了协议——谁来决定 Agent 在什么时候调用哪个 Server？谁来处理 Server 返回的错误？谁来限制 Agent 的调用频率和权限？Agent 编排层需要回答这些问题，它在 MCP 协议之上提供**调用策略**：串行还是并行、超时重试策略、结果校验、以及审计日志。

## 三、主流编排框架的对比分析

基于上述问题域，我们评估四个在 2025~2026 年最主流的开源 Agent 编排框架。评估标准不是「哪个最好」，而是「哪个最适合商域的具体约束」。

### 3.1 LangGraph（LangChain 官方）

LangGraph 是目前在生产级 Agent 应用中采用最广泛的编排框架。它的核心抽象是**状态图（StateGraph）**：开发者定义节点（每个节点是一个 Python/TypeScript 函数，可以调用 LLM、工具、或纯逻辑代码）和边（条件转移逻辑），然后由运行时按照图结构执行。

**为什么它适合商域：**

商域的赛事引擎本质上就是一个状态机——`round → decision → settlement → next_round` 的循环与 LangGraph 的图结构高度同构。这意味着如果未来需要让 LLM Agent 参与某些决策环节（例如作为「市场分析师 NPC」在回合间隙发布动态新闻），可以直接在同一个图模型中嵌入，而不需要推翻现有的回合制架构。更重要的是，LangGraph 的**持久化（Persistence）**机制支持 checkpoint：如果一场比赛进行中服务重启，可以从上一个 checkpoint 恢复状态。这对于长周期的创业孵化任务（OPC）尤为重要。

LangGraph 的**人工介入（Human-in-the-loop）**支持也很成熟——可以在任意节点插入 `interrupt`，等待人类输入后继续。这与商域中教师审批、学生确认的场景直接对应。

**不足之处：** 学习曲线较陡，对「图思维」的要求高；对于简单的单 Agent 场景显得过重；在超大规模并发（数千场同时进行的比赛）下的性能尚未经过充分验证。

### 3.2 AutoGen（Microsoft）

AutoGen 的设计哲学是**对话驱动**——Agent 之间通过自然语言消息进行协作。它的核心抽象是 `ConversableAgent` 和 `GroupChat`，多个 Agent 在一个群聊环境中轮流发言，由「群聊管理器」决定下一个发言者。

**为什么它值得参考：**

AutoGen 的 GroupChat 模式非常适合商域中「多 NPC 辩论/协商」的场景。比如在一个模拟商会场景中，陈叔（保守派）、小投机（激进派）、李供应链（效率派）围绕「是否应该扩大生产规模」展开讨论，学生旁听并可在关键时刻插话。AutoGen 的群聊管理器可以配置为「轮流发言」「按角色优先级」「或基于内容相关性选择下一位发言者」，这种灵活性是 LangGraph 的显式图结构所不具备的。

AutoGen 还支持**代码执行 Agent**——Agent 可以生成并执行 Python 代码来完成复杂计算。这在 OPC 的数据分析任务（如财务模型计算）中有直接应用价值。

**不足之处：** 对话驱动的本质意味着行为的确定性较低，同一个场景两次运行可能产生不同结果，这与教育场景中对可复现性的要求存在张力；群聊模式在消息历史膨胀后的上下文管理不够优雅；微软对 AutoGen 的维护策略在 2025 年有所调整，社区生态的稳定性需要观察。

### 3.3 CrewAI

CrewAI 是一个高度**角色驱动**的框架。开发者首先定义 Agent 的「角色（Role）」「目标（Goal）」「背景故事（Backstory）」，然后将任务（Task）分配给这些 Agent，由 Crew（团队）自动协调任务的执行顺序和依赖关系。

**为什么它适合 NPC 设计：**

商域的 NPC 体系（`90-AI 对手 NPC 化与成长演化系统 PRD`）已经有了明确的角色定义——陈叔是「蓉城老粮商」，价值观是「宁可少赚，不可大亏」。CrewAI 的 Agent 定义方式与这种角色化设计高度一致。在 Phase C~D 的「Persona 引擎」建设中，可以直接将 Persona YAML 映射为 CrewAI 的 Agent 配置，实现「角色设计即代码」。

CrewAI 的任务委托机制也很有启发：当一个 Agent 遇到不属于自己职责范围的问题时，可以自动将任务「移交（Delegate）」给更合适的 Agent。这与商域中 AI 教练 Athena 需要将某些专业问题转交给「财务顾问 NPC」或「市场分析 NPC」的场景直接对应。

**不足之处：** CrewAI 对执行流程的控制粒度较粗（不如 LangGraph 的显式图结构）；任务之间的状态传递机制相对简单；在多轮复杂交互场景下不如 LangGraph 灵活。

### 3.4 Swarm（OpenAI）

Swarm 是 OpenAI 在 2024 年底发布的一个**极简多 Agent 编排示例**，核心代码仅约 100 行。它的设计极其简洁：每个 Agent 有一个名字、一套指令、一组可用函数；Agent 之间通过「交接（Handoff）」转移控制权。

**为什么它值得了解：**

Swarm 的极简设计让它成为理解多 Agent 编排本质的最佳教学材料。虽然 OpenAI 已明确表示 Swarm 是「教育性质」而非「生产框架」，但其核心概念——**Agent 作为状态机、Handoff 作为状态转移、函数调用作为副作用**——是所有编排框架的共同底层。

对于商域而言，Swarm 的价值在于**概念验证（PoC）**：在投入 LangGraph 的复杂图结构之前，可以用 Swarm 快速验证「一个 NPC 将对话交给另一个 NPC」的基础交互模式是否满足教学需求。

**不足之处：** 已停止活跃维护；无持久化、无错误恢复、无人工介入；不适合任何生产场景。

### 3.5 框架对比总表

| 维度 | LangGraph | AutoGen | CrewAI | Swarm |
|------|-----------|---------|--------|-------|
| **核心抽象** | 状态图（节点+边） | 对话（群聊） | 角色+任务团队 | Agent+Handoff |
| **确定性** | 高（显式图结构） | 中（对话驱动） | 中（任务列表驱动） | 中 |
| **多 Agent 协作** | 显式编排（并行/条件） | 群聊协商 | 任务委托 | 简单交接 |
| **持久化/恢复** | ✅ 内置 Checkpoint | ⚠️ 需自行实现 | ⚠️ 有限支持 | ❌ 无 |
| **人工介入** | ✅ 内置 Interrupt | ⚠️ 需自行实现 | ⚠️ 有限支持 | ❌ 无 |
| **工具调用** | ✅ 与 LangChain 工具链深度集成 | ✅ 代码执行强 | ✅ 标准 Python 函数 | ✅ 极简函数调用 |
| **学习曲线** | 陡峭 | 中等 | 平缓 | 极简 |
| **维护状态** | 活跃（LangChain 官方） | 调整中 | 活跃 | 已停止 |
| **商域适配度** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐（仅 PoC） |

## 四、商域各子系统的编排映射

不同的子系统对 Agent 编排有不同的需求强度和模式偏好。以下是将编排框架映射到具体业务场景的初步分析。

### 4.1 赛事引擎（Trading / TechVenture）

赛事引擎是商域对确定性和性能要求最高的子系统。在 Phase A~B 期间，赛事引擎应**完全不引入 LLM Agent 编排**——对局内的所有决策由规则引擎驱动，编排器的引入将带来不可接受的延迟和不确定性。

但存在两个未来的编排切入点：

**局间动态新闻生成（Phase C-）**：在回合间隙，由一个轻量级的 LangGraph 子图生成与当前市场状态相关的动态新闻。这个子图包含三个节点：「读取市场状态」→「生成新闻草稿」→「事实校验（护栏）」。它运行在独立的异步进程中，不影响主引擎的 tick 推进。

**NPC 赛后点评（Phase C-）**：对局结束后，LangGraph 子图根据 `match_npc_facts` 中的事实数据生成 NPC 的个性化点评。节点包括：「加载 NPC Persona」→「聚合事实」→「生成点评」→「护栏检查（禁止泄露其他玩家信息）」。

### 4.2 AI 教练 Athena

Athena 是商域中最有可能深度使用 Agent 编排的子系统。它的核心交互模式——学生提问 → 系统理解意图 → 检索相关记忆/知识 → 生成回应——天然是一个多步骤的流程。

推荐的编排模式：

```
[学生输入] → [意图分类节点]
                ↓
    ┌───────────┼───────────┐
    ↓           ↓           ↓
[赛后复盘]  [策略咨询]   [生涯规划]
    ↓           ↓           ↓
[事实检索]  [知识图谱]   [进度查询]
    ↓           ↓           ↓
[生成回应]  [生成建议]   [生成计划]
    ↓           ↓           ↓
    └───────────┴───────────┘
                ↓
          [护栏校验]
                ↓
          [人工介入检查]
                ↓
          [输出给学生]
```

这里 LangGraph 的条件边和人工介入节点是核心能力。`意图分类节点`可以用一个小模型（或规则分类器）实现，`护栏校验`节点是一个纯逻辑函数，不依赖 LLM。

### 4.3 NPC 生涯对话系统

NPC 在生涯模式中的对话涉及状态管理（当前章节、关系度、已解锁内容）、内容生成（对话文本）、以及多 NPC 协作（如商会场景）。

推荐的编排模式：

**单 NPC 对话**：每个 NPC 维护一个独立的 LangGraph 状态图，状态包括「当前章节」「关系度」「待解锁内容」「对话轮次」。当学生与 NPC 对话时，图根据输入决定是「继续当前话题」「推进章节」「触发任务」还是「结束对话」。

**多 NPC 协作场景**：使用 AutoGen 的 GroupChat 模式（或 LangGraph 的并行节点）管理多个 NPC 的轮流发言。编排器维护一个「场景状态」——当前议题、每位 NPC 的立场、已达成共识的要点——并在每轮选择最合适的下一位发言者。

### 4.4 OPC 创业孵化流水线

OPC 的五个阶段（IDEATE → VALIDATE → BUILD → LAUNCH → SCALE）是一个典型的**长周期工作流**，每个阶段内部包含多个串行和并行的任务。

推荐的编排模式：

使用 LangGraph 的**子图（Subgraph）**机制：每个阶段是一个独立的子图，主图负责阶段之间的流转。子图内部的任务可以是串行的（如「生成 BMC → 教师审批 → 发布」），也可以是并行的（如「同时执行市场调研和竞品分析」）。

LangGraph 的持久化机制在这里至关重要——如果一个 BUILD 阶段的任务需要运行 30 分钟（如 AI 生成代码），服务重启后可以从 checkpoint 恢复，而不是重新开始。

### 4.5 知识图谱与 RAG

Atlas 知识图谱在 Phase C~D 需要从静态 JSON 演进为动态知识库。Agent 编排在这里的作用是**协调检索与生成的关系**：不是简单地将检索结果塞进 prompt，而是让编排器决定「是否需要检索」「检索什么」「检索结果是否足够回答用户问题」「是否需要进一步检索」。

LangGraph 的「检索 → 评估 → 决定（继续检索或生成回答）」循环模式非常适合这种场景。每个节点都有明确的职责边界，便于调试和优化。

## 五、技术选型的渐进式策略

基于上述分析，我们提出一个与 Phase 门控对齐的渐进式技术策略。

### 5.1 核心原则

**原则一：规则引擎是地基，编排是上层建筑。** 在任何涉及计分、排名、资金变动的场景中，规则引擎拥有最终权威。编排器可以生成建议、解释、对话，但不能直接修改比赛状态。

**原则二：先单 Agent，后多 Agent。** 在 Phase C 之前，所有 LLM 调用都通过单一入口（如 Athena Service）管理，内部可以有简单的步骤分解，但不需要完整的编排框架。Phase C 开始引入 LangGraph 管理 Athena 的复杂对话流，Phase D 扩展到多 NPC 协作，Phase E 才在 OPC 中启用完整的多 Agent 团队编排。

**原则三：编排即配置。** 教研人员应该能够通过 YAML 或可视化界面调整 Agent 的行为，而不需要修改代码。这意味着编排图的节点和边定义需要从代码中抽离出来，以声明式配置的形式存储（类似当前 `ai_strategies` 的 YAML 配置方式）。

### 5.2 Phase 对齐的技术路线

| Phase | 编排范围 | 框架 | 关键能力 |
|-------|---------|------|---------|
| **A~B** | 无（纯规则引擎） | — | 保持当前架构稳定 |
| **B3** | Athena 简单多轮对话 | 模板+状态机（无框架） | 意图分类、上下文管理 |
| **C-** | Athena 复杂对话 + NPC 赛后点评 | LangGraph 轻量引入 | StateGraph、人工介入 |
| **C** | Quest 服务 + 动态新闻 | LangGraph 扩展 | 子图、持久化 |
| **D** | 多 NPC 协作 + 知识图谱 RAG | LangGraph 为主 + AutoGen 参考 | 并行节点、条件边、GroupChat 模式借鉴 |
| **E** | OPC 创业孵化流水线 + MCP 工具调用 | LangGraph + MCP SDK | 子图嵌套、工具调用标准化、Checkpoint 恢复 |

## 六、关键设计模式

以下是在商域场景中最可能需要的设计模式，它们不是某个框架特有的，而是 Agent 编排领域的通用最佳实践。

### 6.1 护栏模式（Guardrails）

在教育场景中，Agent 的输出必须经过多层校验：不能泄露其他玩家的策略、不能给出有害的财务建议、不能生成不当内容。护栏不是单个检查点，而是一系列分布在编排图各节点的校验层。

**实施建议：** 在 LangGraph 中，每个生成节点后都连接一个 `guardrail_node`，它是一个纯逻辑函数（不调用 LLM），负责检查输出是否违反预设规则。如果违反，触发回退路径（返回预设的安全回复，或转人工审核）。

### 6.2 记忆分层模式

Agent 的记忆不应是单一的「历史消息列表」，而应分为三层：**短期工作记忆**（当前对话的最近几轮）、**中期事实记忆**（从对局数据中提取的关键事实，如「该学生在上一场比赛中三次高杠杆操作」）、**长期画像记忆**（学生的整体学习风格、偏好、成长轨迹）。

**实施建议：** 短期记忆由 LangGraph 的 State 对象管理；中期事实记忆存储在 `match_npc_facts` 和 `career_profiles` 中，通过查询节点检索；长期画像记忆在 Phase C 后引入向量数据库（如 ChromaDB/Qdrant）支持语义检索。

### 6.3 人机协作模式

不是所有决策都适合交给 AI。编排图需要明确标识哪些节点必须等待人类输入（如教师审批创业计划书）、哪些节点可以自动执行但事后需要人类确认（如 AI 生成的新闻稿）、以及哪些节点可以完全自主（如赛后数据统计）。

**实施建议：** 在 LangGraph 中使用 `interrupt` 机制实现人工介入节点。每个介入节点配置超时策略——如果人类在设定时间内未响应，执行默认回退行为（如「保存草稿，稍后提醒」）。

### 6.4 降级链模式

LLM 服务可能出现延迟过高、配额耗尽、或内容被过滤的情况。编排器需要为每个 LLM 依赖的节点设计降级链：首选模型 → 备用模型 → 规则模板 → 静态回复。

**实施建议：** 在节点内部封装模型调用逻辑，捕获所有异常并根据预设策略选择降级路径。所有降级事件记录到监控日志，供后续分析。

## 七、风险与约束

引入 Agent 编排不是无成本的。以下是商域需要特别注意的风险。

**延迟风险。** LLM 调用通常需要 1~5 秒，这与赛事引擎的毫秒级要求形成鲜明对比。任何涉及 LLM 的流程都必须设计为异步执行，绝不能阻塞比赛的主推进循环。

**成本风险。** 一个复杂的多 Agent 工作流可能在单次交互中消耗数万 Token。OPC 的孵化流水线如果每个任务都调用 GPT-4 级别模型，单次创业模拟的成本可能超过 10 美元。需要在编排层实现 Token 预算管理：每个工作流实例有预设的 Token 上限，接近上限时触发降级或中断。

**可解释性风险。** 当 Agent 给出了一个建议，学生或教师需要理解「这个建议是怎么来的」。编排图的显式结构天然比端到端的 LLM 调用更可解释——可以通过可视化界面展示「Agent 先检索了你的比赛数据，然后查询了知识图谱中的相关概念，最后综合生成了这个建议」。

**公平性风险。** 在正式比赛中，如果 NPC 的行为由 LLM Agent 驱动，必须确保所有玩家面对的 NPC 在相同条件下行为一致。这要求编排流程是确定性的（相同的输入总是产生相同的输出），或者至少是可审计的（所有随机决策记录种子值）。

## 八、待探索问题

1. **编排配置的可视化编辑。** 教研人员能否通过拖拽方式设计 NPC 的对话流程图，而不需要编写代码？这与 `89-赛事工坊` 的 YAML 编辑器设计有何关联？

2. **编排与现有事件系统的集成。** 商域已有基于 FastAPI 的事件机制（如 `match.finished`）。Agent 编排的异步任务如何与现有事件总线协作？是独立运行还是通过事件触发？

3. **多语言支持。** 如果未来平台支持英文版本，Agent 编排层是否需要为不同语言维护独立的图结构，还是通过国际化层统一处理？

4. **编排的性能基准。** 在 SQLite 单库单进程架构下，LangGraph 的持久化写入是否会成为瓶颈？何时需要考虑将编排状态存储分离到独立的存储（如 Redis）？

## 附录 B：术语表

| 术语 | 定义 |
|------|------|
| **Agent** | 一个能够感知环境、做出决策并执行行动的自主实体。在商域语境中，通常指由 LLM 驱动的智能体（如 Athena、NPC）。 |
| **编排（Orchestration）** | 管理多个 Agent 或任务之间的执行顺序、状态传递和协作关系的机制。 |
| **StateGraph** | LangGraph 的核心抽象，将应用流程建模为有状态的有向图，节点处理状态，边控制流转。 |
| **Checkpoint** | LangGraph 的持久化机制，定期将图的完整状态保存到存储中，支持中断恢复。 |
| **Human-in-the-loop** | 在工作流的关键节点暂停执行，等待人类输入后再继续的模式。 |
| **MCP（Model Context Protocol）** | Anthropic 推出的标准化协议，允许 LLM 以统一方式调用外部工具和服务。 |
| **护栏（Guardrails）** | 在 Agent 输出前对内容进行检查和过滤的机制，防止有害、不当或违规输出。 |
| **子图（Subgraph）** | LangGraph 中可以被其他图作为节点调用的独立图结构，支持模块化设计。 |
