# 01 - 技术栈与系统架构建议

> 基于现有 TechVenture 后端（TypeScript + Express + 文件持久化）出发，面向"在线体验、游戏化教学、生涯成长"新平台的系统建设思路。

---

## 一、对现有技术资产的评估

| 维度 | 现状 | 评估 |
|------|------|------|
| 后端语言 | TypeScript / Node.js | 良好，生态丰富，适合实时交互 |
| Web 框架 | Express 4.x | 够用，但未来可考虑更现代的框架（如 Fastify / NestJS） |
| 持久化 | 内存 + 定时写入 JSON 文件 | **风险点**：单节点、无并发安全、难以横向扩展 |
| 前端 | 无（或外部独立项目） | 需要统一规划 |
| 实时通信 | 无（轮询） | 需要引入 WebSocket / SSE |
| 部署 | 本地 bat 启动 | 需要容器化与 CI/CD |

**结论**：现有结算引擎（v6Engine）逻辑清晰、参数化程度高，是核心资产；但基础设施层需要全面升级以支撑在线化、多班级并发、用户成长体系等需求。

---

## 二、推荐技术栈（分层架构）

### 2.1 前端层

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| 学生参赛端（Web） | **React 18 + TypeScript + Tailwind CSS** | 生态成熟、组件化、易于设计系统统一 |
| 教师管理端（Web） | **同上**，或 Vue 3 | 若团队有 Vue 经验也可统一用 Vue |
| 大屏展示端 | **React + Canvas / ECharts** | 数据可视化需求高 |
| 移动端适配 | **PWA 或小程序** | 学生主要使用手机，PWA 成本低，小程序传播强 |
| 3D/游戏化场景 | **Phaser 3** 或 **PixiJS** | 2D 游戏首选；若做复杂经营模拟可用 Unity WebGL |

### 2.2 后端层

| 层级 | 推荐方案 | 理由 |
|------|----------|------|
| API 网关 / BFF | **NestJS** 或保持 Express 渐进升级 | NestJS 提供模块化、依赖注入、WebSocket 集成，适合大型项目 |
| 结算引擎 | **保留现有 TS 引擎**，抽取为独立 `npm workspace` | 核心资产，纯函数易于单元测试 |
| 实时通信 | **Socket.io** 或 **SSE** | 房间制非常适合"班级-对局"模型 |
| 任务队列 | **BullMQ (Redis)** | 用于异步结算、排行榜计算、数据导出 |
| 缓存 | **Redis** | 会话、热数据、排行榜、限流 |

### 2.3 数据层

| 数据类型 | 推荐方案 | 理由 |
|----------|----------|------|
| 主业务数据 | **PostgreSQL** | 关系型数据（用户、班级、对局、回合） ACID 保障 |
| 日志 / 事件流 | **ClickHouse** 或 PG 分区表 | 学生操作日志、教学分析需要大量时序数据 |
| 文件 / 静态资源 | **OSS (阿里云/腾讯云)** 或本地 MinIO | 学生上传的商业计划书、图片等 |
| 配置 / 规则 | **JSON Schema + 数据库** | 商赛规则版本化管理，便于 A/B 测试 |

### 2.4 DevOps & 基础设施

- **容器化**：Docker + Docker Compose（开发）/ Kubernetes（生产）
- **CI/CD**：GitHub Actions / GitLab CI
- **监控**：Prometheus + Grafana（服务端），Sentry（前端异常）
- **日志**：Loki 或 ELK 精简版

### 3.2 核心领域模型（DDD 思路）

```
User (用户) ──1:N──► StudentProfile (学生档案 / 局外成长)
                ──N:M──► Class (班级)
                ──1:N──► GameSession (对局参与)

Class ──1:N──► GameSession (对局/比赛)
Teacher ──1:N──► Class

GameSession ──1:N──► Round (回合)
Round ──1:N──► TurnDecision (回合决策)
Round ──1:1──► SettlementResult (结算结果)

GameSession ──N:M──► Team (队伍快照，对局内数据)
Team ──1:N──► CityState (城市维度属性)
```

**关键区分**：
- `User` 是平台账号（局外长期存在）
- `StudentProfile` 是成长档案（经验、徽章、技能树、解锁内容）
- `Team` 是对局内实体（每局重新创建或关联到 User）
- 这样实现"一个账号参与多局，局外成长持续积累"

### 3.3 结算引擎的演进建议

现有 `v6Engine` 是纯函数 `settleRoundV6(ctx) => output`，这是非常好的设计。

建议演进：
1. **抽取核心库**：`@bizsim/engine-core`，包含 config + contracts + settleRound，不依赖 Express
2. **版本化管理**：规则版本如 `v6.0`, `v6.1`, `v7.0`，数据库记录每局使用的规则版本
3. **确定性重放**：结算依赖 `Math.random()`（noise），应改为可种子化的伪随机（seedrandom），支持完全重放
4. **并行计算**：大规模排行榜可用 Worker Threads 并行结算多局
5. **规则热更新**：通过数据库配置表 + 缓存刷新，实现不停机调整参数

## 四、关键非功能性需求

| 需求 | 策略 |
|------|------|
| 高并发（开学季） | 无状态 API 服务 + Redis 共享会话 + 数据库连接池 |
| 低延迟（实时对战） | WebSocket 房间模型 + 本地缓存热数据 |
| 数据安全（学生信息） | 等保二级/三级、数据加密、最小权限原则 |
| 可扩展性（新玩法） | 模块化微服务或至少模块化单体（Modular Monolith） |
| 多租户（学校/机构） | 数据库级别隔离或 schema 级别隔离 |

## 五、渐进式迁移路线

如果希望从现有代码平滑过渡，而非推倒重来：

| 阶段 | 目标 | 行动 |
|------|------|------|
| Phase 1 | 在线化 | 为现有 Express 增加 PostgreSQL 持久化；开发 React 前端；部署到云服务器 |
| Phase 2 | 实时化 | 引入 Socket.io；增加教师端控制台；大屏数据推送 |
| Phase 3 | 成长化 | 增加 User 系统；设计经验/徽章体系；局外成长数据与对局解耦 |
| Phase 4 | 平台化 | 多课程模板；自定义规则编辑器；学校管理后台；数据分析看板 |

## 六、技术风险与规避

1. **JSON 文件并发写入**：立即替换为数据库，否则多班级同时使用会丢数据
2. **前端与后端割裂**：建议统一仓库用 Monorepo（pnpm workspace / Turborepo），共享 TypeScript 类型
3. **规则硬编码**：现有 `config.ts` 很好，但未来需要从数据库读取，建议保留 TS 类型 + 运行时校验（Zod）
4. **无测试**：结算引擎必须补充单元测试（Jest），每条规则变动都需回归
