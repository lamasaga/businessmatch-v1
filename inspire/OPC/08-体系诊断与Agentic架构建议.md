## 一、评审结论摘要

| 维度 | 判断 |
|------|------|
| **战略方向** | 一致且先进：五域闭环、生涯主线、OPC 作「首项目」终局、声明式赛制 |
| **主要问题** | 不是缺功能，而是 **叙事冲突、AI 面孔过多、思考链断裂、周期不匹配、三套智能运行时未收敛** |
| **Agentic 方向** | 应从「多 Agent 展示」转为 **单一 Pedagogy Orchestrator + 事件驱动 + 临时 Worker + 强制人机检查点** |
| **实施建议** | 先合并教练层与解锁逻辑，再扩 OPC 员工数量（见 [八、改版路线图](#八改版路线图对照-07)） |

## 二、不和谐与系统性风险

### 2.1 两套「成功标准」并存

| 叙事 A（成长花园） | 叙事 B（竞技/门槛） |
|--------------------|---------------------|
| 比昨天的自己进步 | 赛季榜、ELO、排名 |
| 失败是养分 | 商赛前 30% 解锁 OPC（`05-` 融合路径） |
| 多元价值 | 高权重 XP 来自对局名次（`03-` 激励闭环） |

**风险**：学生收到矛盾信号；竞争型刷商赛，合作型/内向型长期进不了 OPC。

**整改方向**：

- OPC 解锁 **主路径**：课程 + 图谱 + 主动申请（Athena 背书）  
- 商赛路径改为 **资源包加成**（Legacy），非唯一资格  
- 任何排行榜旁 **同屏展示素养维度变化**（成长榜硬编码）

### 2.2 AI 角色过多（用户心智负担）

当前面向学生的「会说话的实体」至少包括：

- Athena（全局教练）  
- Rival（对手）  
- Cortex + 13 名 AI 员工  
- Gateway 评审（隐性 AI）  
- Demia（叙事层，易被感知为「市场声音」）

**风险**：「我该问谁？」教师亦难以定位问题层级。

**整改方向**：对外 **一个教练品牌**；OPC 内为「项目模式 + 虚拟团队工具」，员工为 **临时 Worker**，非常驻 13 个聊天入口。

### 2.3 交互范式分裂

| 场景 | 范式 |
|------|------|
| Athena / Rival | 对话式 |
| OPC 设计 | 管理者–执行者（任务 brief + 验收） |
| 商赛 | 表单/滑块决策 |

**风险**：学生不会写 brief；在 OPC 仍用「聊天糊弄」。

**整改方向**：统一 **任务卡片 UI**；对话仅作为 brief 的输入方式之一，由 Cortex **解析为结构化需求**（见 `ai-employee-design/04-人机交互协议.md`）。

### 2.4 学习链：「外包思考」断层

| 环节 | AI 边界 | 风险 |
|------|---------|------|
| 商赛 + Athena | 不给最优数值 | 逼学生决策 ✓ |
| OPC 员工 | 可产出完整 BMC/代码 | 学生仅点验收 ✗ |

**整改方向**：每任务强制 **Human Artifact**（学生先交假设/修改说明 → 员工再执行；验收须指出「我改了员工哪几处」）。

### 2.5 学段与功能跨度

同一平台覆盖：小学财商、高中商战、MBA 内容、16 赛制、OPC 真实创业、支付与沙箱。

**风险**：功能超市感；教师培训成本指数上升；MVP 演示与生产落差损害信任。

**整改方向**：**学段强分流**（默认路径、可见模块、AI 策略）；课堂版 OPC（约 4 周）与社团版（约 12 周）两套 SOP。

### 2.6 三套智能运行时

| 运行时 | 机制 |
|--------|------|
| CyberCore | 声明式 YAML + 状态机 |
| 平台 AI | Athena / Demia / Rival |
| OPC | LangGraph + MCP + 多员工 |

**风险**：规则不一致、日志不统一、运维与教研难以理解全貌。

**整改方向**：**Student OS** 统一编排；CyberCore 与 OPC Worker 均作为 **子图/工具**，事件格式统一 CloudEvents。

## 三、教学逻辑问题

1. **先赛还是先学**：解锁偏重商赛 → **先竞技后建构**；更符合建构主义的是概念 → 低 stakes 练习 → 综合任务。  
2. **评价与目的脱节**：排行榜驱动日活，与五维/创业力 Rubric 反馈不同步。  
3. **性格适配过度承诺**：青少年人格不稳定；推荐错误损害信任（见 `15-性格分类框架`）。  
4. **教师责任模糊**：宣称 AI 减负，但 Gateway/伦理需教师背书；L0 旁观者与质量责任未制度对齐。  
5. **诚信标准分裂**：商赛与 OPC 对「代劳/刷分」标准不一致；Ethos 应全平台一致启用。

## 四、用户体验摩擦

| 摩擦 | 表现 | 改进 |
|------|------|------|
| 入口过多 | 五域 + OPC + 展示 + 国富论 | 生涯首页 **今日 3 件事**，其余二级 |
| 反馈延迟 | 复盘/员工任务异步 | 进度条 + **这一步在学哪项素养** |
| 成就可信度 | Mock 与真后端混用 | 演示模式显式标注 |
| 移动端 | 重仪表盘、谈判长文本 | Quest/微课 mobile-first |
| 失败体验 | 排名靠后挫败 | 成长榜 + Athena 过程肯定（产品硬编码） |
| 未成年真实交易 | LAUNCH 风险 | 默认模拟；真实收入需家长授权流 |

## 五、AI 辅助优先级（何处真提升）

| 优先级 | 环节 | AI 应做 | 避免 |
|--------|------|---------|------|
| **P0** | **Student OS（统一教练）** | 根据全状态推 **唯一下一步** | 五入口各推各的 |
| **P0** | **跨域学生模型** | 学习+决策+项目一份画像 | 重复问诊 |
| **P0** | **商赛赛后复盘** | Debrief + 图谱薄弱点 | 局内给答案 |
| **P1** | **教师 Copilot** | 班级风险、Gateway 批量摘要 | 替代教师担责 |
| **P1** | **OPC 拆单** | NL → brief + Rubric（Cortex） | 未经确认开干 |
| **P1** | **Gateway 混合评审** | 规则 70% + LLM 解释不通过原因 | 黑箱分 |
| **P2** | Demia | 规则算分 + 短叙事 | LLM 改数值 |
| **P2** | Rival | 谈判 + 空头承诺检测 | 与 ELO 混用 |
| **P3** | 内容生成 | 教师出题/案例变体 | 未经审核上线 |

**相对次要**：13 个员工全员重度人格化——教学上 **3～5 核心角色 + 其余能力包** 通常足够。

## 六、推荐 Agentic 架构：Pedagogy OS

### 6.1 范式对比

| 伪提升 | 真提升 |
|--------|--------|
| 多 ChatGPT 皮肤 | 减少下一步选择疲劳 |
| 员工自动写完项目 | 学生 artifact + Rubric 可追溯 |
| 13 Agent 互聊 | 单 Orchestrator + 临时 Worker |
| AI 评审黑箱 | 通过/不通过 + 证据链可点击 |
| 演示 Mock | 同一事件与画像贯穿 |

### 6.2 架构图

```
                    ┌─────────────────────────────────┐
                    │   Student OS（Pedagogy Orchestrator）│
                    │   · 读 Career 全状态（唯一入口）    │
                    │   · 学段/目标策略（Policy 层）      │
                    │   · 决定：课/局/任务/仅观察         │
                    │   · 统一记忆写入（Event + Graph） │
                    └───────────────┬─────────────────┘
                                    │
          ┌─────────────────────────┼─────────────────────────┐
          ▼                         ▼                         ▼
   ┌─────────────┐          ┌─────────────┐          ┌─────────────┐
   │ Skill:Tutor │          │ Skill:Arena │          │Skill:Venture│
   │ Athena 内核  │          │ Debrief     │          │ Cortex 子图  │
   │ RAG/追问    │          │ Demia/Rival │          │ Worker 派遣  │
   └──────┬──────┘          └──────┬──────┘          └──────┬──────┘
          │                         │                         │
          └─────────────────────────┴─────────────────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    │  Tool Layer (MCP)              │
                    │  atlas · memory · sandbox ·    │
                    │  ethos · deploy · report       │
                    └───────────────────────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    │  CyberCore（赛制，非 Agent）      │
                    │  声明式状态机 · 确定性结算       │
                    └───────────────────────────────┘
```

### 6.3 六条设计原则

1. **一个面向学生的主 Agent**：用户只认「商业教练」；OPC 为 **项目模式**，非第二品牌。  
2. **员工是 Worker，非常驻 Agent**：按任务 spawn LangGraph 子图，完成即归档。  
3. **Human-in-the-loop 是图节点**：计划确认 → 执行 → 验收 → 反思，均为 `interrupt`。  
4. **Policy 与 LLM 分离**：学段、伦理、防沉迷、商赛不给答案 — 硬编码；LLM 负责语言与推理。  
5. **事件驱动优先于聊天驱动**：`match.finished`、`task.reviewed` 触发复盘。  
6. **共享记忆**：`student_id` 下掌握度、决策风格、项目态、失败记录 — 事件溯源 + 向量检索。

### 6.4 LangGraph 落地形态（示意）

```yaml
student_os_graph:
  nodes:
    - assess_state          # 读 PG + 最近事件
    - plan_next_action      # 输出：domain + resource_id + rationale
    - await_human_confirm   # interrupt（可选）
    - dispatch_skill        # 路由到 tutor | arena_coach | venture
    - write_memory          # 统一记忆层
  skills:
    venture:
      subgraph: OPC_task_flow   # Cortex → Worker → Gateway → review_interrupt
    arena_coach:
      subgraph: post_match_debrief  # 仅赛后；局内无 LLM 策略
    tutor:
      subgraph: rag_tutor         # 苏格拉底；高 stakes 拒绝给数值
```

### 6.5 与 OPC 13 员工的关系

| 原设计 | 调整后 |
|--------|--------|
| 13 个常驻「同事」 | **角色目录** + 按任务实例化 Worker |
| 每员工独立聊天页 | **任务时间线** + 必要时侧边对话 |
| Cortex 与 Athena 并列 | Cortex 作为 Student OS 的 `venture` 子模式 |

## 八、改版路线图（对照 07）

### 8.1 对照表：`07-实施路径` → 调整后

| `07` 原 Phase | 原重点 | **建议调整** | 理由 |
|---------------|--------|--------------|------|
| Phase A | 解锁 + IDEATE + 3 员工 | **先做 Student OS MVP + 解锁主路径改版 + IDEATE**；员工仅 BA/CP | 先统一教练，再扩角色 |
| Phase B | VALIDATE/BUILD + 全 MCP | BUILD 前加 **Human Artifact**；MCP 先 atlas+ethos+sandbox | 防外包思考 |
| Phase C | 商赛联动 + 教师看板 | **教师 Copilot** 提前到 Phase B；商赛→资源包非门槛 | 减负与叙事一致 |

### 8.2 推荐新 Phase 0（2～3 周）：叙事与编排地基

| 任务 | 产出 |
|------|------|
| 定义 `student_os` 状态模型（单表或视图） | 全平台读一份画像 |
| 合并前端教练入口 | 仅「教练」浮窗 + 项目模式切换 |
| 解锁规则改版 | 课程/图谱/申请为主；商赛为加成 |
| 事件规范 v1 | `career.*` + `OPC.*` + `arena.*` 统一 trace_id |
| 生涯首页「今日 3 件事」 | 由 Student OS 规则生成（可先规则引擎） |

## 九、战略级三项改动

若资源有限，**优先做且只做这三件**：

1. **合并 AI 面孔**  
   对外一个「商业教练」；OPC = 项目模式 + 工具化团队，不另立 15 个品牌。

2. **统一进步叙事**  
   任何排名/XP 同屏素养变化；OPC 不与「只有赢家」绑定。

3. **上 Student OS 编排层**  
   再扩 OPC 员工数；否则复杂度先压垮体验与教学可信度。
